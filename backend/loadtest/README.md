# Навантажувальне тестування API (Locust)

Інструменти лише **вимірюють** продуктивність ендпоінтів — у коді застосунку нічого не змінюється.
Сценарій: запустити сервер у «бенчмарк-режимі» → засіяти дані → прогнати `run.py` → після оптимізацій
прогнати ще раз → порівняти `compare.py`.

```
loadtest/
  common.py      — хост, облікові дані тестового користувача
  seed.py        — створює/перевикористовує користувача loadtest-bench@example.com і фіксований датасет
  locustfile.py  — задачі Locust: по одній на ендпоінт (+ змішаний сценарій MixedUser)
  run.py         — headless-прогін по кожному ендпоінту, JSON + markdown у results/
  compare.py     — таблиця «до / після»
  results/       — результати (<YYYY-MM-DD_HHMM>_<git-sha>[_label].json / .md)
```

## 1. Встановлення

Locust — окрема залежність, у `requirements.txt` застосунку його немає:

```bash
.venv/Scripts/python -m pip install -r requirements-loadtest.txt
```

Усі команди нижче запускаються з теки `backend/`.

## 2. Сервер для вимірювань

Не міряйте сервер, запущений через `python -m src.app` — там `reload=True`, і `--reload` вимикає воркери
та додає накладні витрати. Запускайте окремий сервер на вільному порту, **завжди з тими самими параметрами**:

```bash
.venv/Scripts/python -m uvicorn src.app:app --host 127.0.0.1 --port 8002 --workers 4 --log-level warning --no-access-log
```

- `--workers N` — фіксуйте число (наприклад, 4 або кількість фізичних ядер) і не змінюйте між «до» і «після».
  Якщо змінюєте — це окремий експеримент, а не порівняння коду.
- `--log-level warning --no-access-log` — вимикає access-лог uvicorn (запис у консоль на кожен запит сильно
  гальмує на Windows). Власний логер застосунку (`src/config.py`) пише INFO у `logs.log` — це частина
  поточної поведінки застосунку, тому для чесного порівняння залишається однаковим в обох прогонах.
- Locust і сервер працюють на одній машині й ділять CPU. Locust використовує одне ядро; якщо в таблиці
  бачите >1000–1500 RPS, вузьким місцем може бути вже сам Locust (на Windows `--processes` не працює).

### Умови, від яких залежать цифри

- Ноутбук **на зарядці**, режим живлення «Найкраща продуктивність» (Windows) — на батареї CPU тротлиться.
- Закрийте важкі програми (браузер з купою вкладок, IDE-індексацію, Docker-контейнери, антивірусне сканування).
- PostgreSQL на тій самій машині, той самий датасет (див. `seed.py --reset`).
- Шум між прогонами на ноутбуці — 5–15 %. Для висновків робіть **3 прогони й беріть медіану**;
  різницю < 10 % вважайте шумом.

## 3. Дані

```bash
.venv/Scripts/python -m loadtest.seed                  # створити або перевикористати
.venv/Scripts/python -m loadtest.seed --reset          # видалити тестового користувача й засіяти заново
.venv/Scripts/python -m loadtest.seed --host http://127.0.0.1:8002
```

Створюється (лише через публічне API, інших користувачів не чіпає) користувач `loadtest-bench@example.com`
і детермінований датасет (`random.Random(42)`): 2000 транзакцій за 12 місяців (UAH + трохи USD/EUR, теги,
нотатки), 6 регулярних платежів, 3 шаблони, 2 цілі-«банки», 1 бюджет. Дати рахуються від дня засіву
(аналітика дивиться на «поточний місяць»), тому **перед серією «до/після» зробіть `--reset`**, щоб обидва
прогони бачили ті самі дані. Облікові дані можна перевизначити змінними `LOADTEST_EMAIL`,
`LOADTEST_USERNAME`, `LOADTEST_PASSWORD`, хост — `LOADTEST_HOST`.

## 4. Прогін

```bash
.venv/Scripts/python -m loadtest.run --list                       # усі ендпоінти та групи
.venv/Scripts/python -m loadtest.run                              # read + write, 20 користувачів, 30 с кожен
.venv/Scripts/python -m loadtest.run --label baseline             # мітка в імені файлу
.venv/Scripts/python -m loadtest.run --only tx_search_text,analytics_overview
.venv/Scripts/python -m loadtest.run --groups heavy --users 4     # opt-in: bcrypt-логін, PDF, OCR чеків
.venv/Scripts/python -m loadtest.run --step --skip-endpoints      # пошук максимального RPS (змішаний сценарій)
.venv/Scripts/python -m loadtest.run --step-endpoints tx_list --skip-endpoints --skip-mixed
```

Що відбувається:

1. **Прогрів** (`--warmup 10`, змішаний сценарій, у результати не потрапляє) — пул з'єднань, кеші БД.
2. **По одному ендпоінту** (`EndpointUser --tags <name>`): `--users 20` віртуальних користувачів без пауз
   (closed loop — кожен шле наступний запит одразу після відповіді), `--duration 30` с. Статистика
   скидається після того, як усі користувачі запущені (`--reset-stats`), тож розгін не псує цифри.
3. **Змішаний сценарій** (`MixedUser`) — усі read/write-задачі з вагами, близькими до реального
   використання (дашборд, список транзакцій, пошук…), тривалість `2 × --duration`.
4. `--step` — **пошук максимального RPS**: 5 → 10 → 20 → 40 … користувачів (`--step-factor`, до
   `--step-max-users`), поки p95 ≤ `--p95-threshold` (500 мс) і помилок ≤ `--max-error-pct` (1 %).

Групи:

- `read` — GET-списки, пошук, аналітика, safe-to-spend, JSON/CSV-експорти, .ics.
- `write` — пари «створити + видалити» (транзакція → кошик → видалити з кошика, регулярний платіж,
  шаблон, ціль, бюджет), «використати шаблон + видалити транзакцію», «поповнити + зняти з цілі»,
  PATCH нотатки. Кількість даних між прогонами не змінюється.
- `heavy` (лише явно) — `auth_login` (bcrypt, повільний за задумом), 4 PDF-звіти, завантаження чека з OCR.
- Не вимірюються взагалі: OAuth Google/GitHub, оновлення курсів НБУ, синхронізація з Google Calendar,
  реєстрація — зовнішні сервіси або одноразові дії.

`--wait 1` додає «час на роздуми» (0.5–1.5 с) між запитами — так моделюється N реальних людей,
а не N максимально агресивних клієнтів.

## 5. Як читати таблицю

| колонка | значення |
|---|---|
| endpoint | назва задачі з `locustfile.py` (тег) і група |
| request | конкретний HTTP-запит; write-задачі містять 2–3 запити |
| RPS | запитів за секунду, які сервер обслужив за 20 одночасних клієнтів (пропускна здатність) |
| p50 / p95 / p99 | мілісекунди: половина / 95 % / 99 % запитів були швидшими. p95 — головна метрика «відчутної» швидкості |
| error % | частка не-2xx відповідей і таймаутів; має бути 0 |
| requests | скільки запитів зроблено за вимірювальне вікно |

Оскільки клієнтів фіксована кількість і пауз немає, RPS ≈ 20 / середній_час_відповіді: вдвічі швидший
ендпоінт дасть приблизно вдвічі більший RPS. Для write-задач RPS кожного рядка — це RPS саме цього
запиту в межах пари. Перцентилі Locust округлює (для > 100 мс — до двох значущих цифр).

Результати: `loadtest/results/<дата>_<sha>[_label].json` (усі цифри + метадані: git sha, «dirty»,
параметри, ОС/CPU) і `.md` з тією ж таблицею.

## 6. Порівняння «до / після»

```bash
.venv/Scripts/python -m loadtest.compare loadtest/results/2026-10-18_1200_abc1234_baseline.json loadtest/results/2026-10-19_1500_def5678_after.json
.venv/Scripts/python -m loadtest.compare A.json B.json -o loadtest/results/diff.md
```

Колонки: RPS до / після, `RPS ×` (> 1 — краще), p95 до / після, `p95 Δ` (від'ємне — краще), помилки.
🟢 — RPS виріс ≥ 10 % без погіршення p95, 🔴 — RPS упав ≥ 10 % або p95 виріс ≥ 20 %. Якщо параметри
прогонів (users / duration / wait) різні, `compare.py` попередить, що цифри не порівнювані.

Рекомендований цикл:

1. `seed --reset`, перезапустити сервер, 3 × `run --label before` → взяти медіанний файл.
2. Оптимізація, коміт.
3. Перезапустити сервер (ті самі `--workers`), 3 × `run --label after`.
4. `compare before.json after.json`.
