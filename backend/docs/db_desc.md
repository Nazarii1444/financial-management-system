
## Управління користувачами

Ядром системи є таблиця **users**.  
Зберігає основну інформацію про користувача:
- `id_`, `username`, `email`, `hashed_password`

Додатково містить:
- базову валюту (`default_currency`)
- часовий пояс (`timezone`)
- баланс (`capital`)
- URL аватару (`avatar_url`)
- план підписки (`subscription_plan`: FREE / PRO)

Реалізує систему ролей (`role`: USER / ADMIN).  
Підтримує двофакторну автентифікацію: `twofa_secret`, `twofa_enabled`.

Є центральною точкою зв'язку з усіма іншими таблицями:  
`transactions`, `goals`, `notifications`, `budgets`, `budget_members`,  
`recurring_transactions`, `notification_preferences`, `receipts`.

---

## Управління валютами

Представлено таблицею **currencies**.  
Зберігає актуальні курси валют:
- `name` — код валюти (USD, EUR, UAH тощо) — первинний ключ
- `rate` — поточний курс відносно базової одиниці

Курси оновлюються щогодини через інтеграцію з API НБУ.  
Використовується для підтримки багатовалютних операцій: конвертації сум транзакцій у валюту користувача.

---

## Система транзакцій

Представлена таблицею **transactions**.  
Є ключовим компонентом фінансової системи.

Зберігає інформацію про операції:
- `id_`, `amount`, `name` (опис), `category_name`, `date`
- `tags` — масив тегів (PostgreSQL `ARRAY(String)`)
- `note` — довільна нотатка
- `currency` — валюта операції

Тип транзакції визначається полем `kind`:  
**EXPENSE**, **INCOME**, **TRANSFER**

Пов'язана з користувачем через `user_id`.  
До транзакції можна прикріпити один або кілька чеків (таблиця `receipts`).  
При кожному записі транзакції автоматично перераховується баланс (`User.capital`) з урахуванням конвертації валют.

---

## Система повторюваних транзакцій

Представлена таблицею **recurring_transactions**.  
Дозволяє налаштувати транзакції, що виконуються за розкладом:
- `name`, `amount`, `kind`, `category_name`, `currency`, `tags`, `note`
- `` — частота: DAILY, WEEKLY, BIWEEKLY, MONTHLY, YEARLY
- `next_run` — дата наступного запуску
- `is_active` — чи активне правило

Раз на хвилину cron-задача перевіряє `next_run` і автоматично створює реальний запис у `transactions`, після чого просуває `next_run` на один крок.

## Система бюджетів

Представлена двома таблицями: **budgets** та **budget_members**.

**budgets** — бюджетні плани:
- `name`, `type` (PERSONAL / FAMILY / BUSINESS), `currency`, `limit_amount`
- `owner_user_id` — власник бюджету

**budget_members** — учасники бюджету (many-to-many між users і budgets):
- `budget_id`, `user_id`
- `role` — роль учасника: OWNER, EDITOR, VIEWER

Один бюджет може мати кількох учасників з різними правами доступу.  
Використовується для сімейного або командного управління фінансами.

---

## Система фінансових цілей

Представлена таблицею **goals**.  
Дозволяє користувачам встановлювати фінансові цілі (ощадні банки / jar):
- `name` — назва цілі
- `target_amount` — необхідна сума
- `saved_amount` — вже накопичена сума
- `currency` — валюта цілі
- `description` — опис
- `deadline` — бажана дата досягнення
- `is_completed`, `completed_at` — статус виконання

Пов'язана з користувачем через `user_id`.

---

## Система чеків та OCR

Представлена таблицею **receipts**.  
Зберігає завантажені файли чеків (зображення або PDF):
- `original_filename`, `stored_filename`, `file_path`
- `content_type`, `file_size`
- `ocr_result` — JSON-результат розпізнавання тексту (pytesseract / pdfplumber)

Прив'язана до користувача (`user_id`) та опціонально до конкретної транзакції (`transaction_id`).  
OCR є опціональним: якщо Tesseract недоступний, поле `ocr_result` залишається `null`.

---

## Сповіщення та налаштування сповіщень

**notifications** — нагадування користувача:
- `deadline` — дата та час події
- `user_id` — прив'язка до користувача

**notification_preferences** — індивідуальні налаштування (1:1 до users):
- `email_enabled`, `push_enabled` — канали доставки
- `budget_limit_alerts` — сповіщення про перевищення бюджету
- `recurring_reminders` — нагадування перед виконанням повторюваних транзакцій
- `goal_milestone_alerts` — досягнення 25/50/75/100% фінансової цілі
- `monthly_summary` — щомісячний підсумковий звіт

Рядок `notification_preferences` створюється ліниво при першому зверненні до `GET /api/settings/notifications`.

## Зв'язки між компонентами

Один користувач (`users`) може мати:
- багато транзакцій (`transactions`) → 1:N
- багато фінансових цілей (`goals`) → 1:N
- багато сповіщень (`notifications`) → 1:N
- багато бюджетів у власності (`budgets`) → 1:N
- участь у багатьох бюджетах через (`budget_members`) → N:M з `budgets`
- багато правил повторюваних транзакцій (`recurring_transactions`) → 1:N
- одне налаштування сповіщень (`notification_preferences`) → 1:1
- багато чеків (`receipts`) → 1:N

Усі залежні записи автоматично видаляються при видаленні користувача (CASCADE).  
Чек при видаленні транзакції не видаляється — `transaction_id` встановлюється в NULL (SET NULL).

## Особливості архітектури

- Використання **Enum** для ролей, типів транзакцій, частот, валют, типів бюджетів
- Підтримка **багатовалютності** з автоматичною конвертацією через таблицю курсів
- Наявність **CheckConstraint** для коректності кодів валют
- Використання **часових міток** (`created_at`, `date`) для відстеження операцій
- **PostgreSQL ARRAY** для зберігання тегів транзакцій
- **JSON** поле для збереження результатів OCR
- **Cascade delete** для всіх залежних сутностей від користувача
- Чітка модульна структура: користувачі → транзакції → бюджети → цілі → сповіщення → чеки

Розроблена база даних забезпечує ефективне управління фінансовою інформацією користувачів, підтримує масштабованість і розширюваність системи. Архітектура дозволяє легко додавати нові функціональні можливості, такі як глибока аналітика витрат, інтеграція з платіжними сервісами або мобільні push-сповіщення.
