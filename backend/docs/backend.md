## 1.1 Технологічний стек та обґрунтування вибору

Серверна частина платформи побудована навколо **FastAPI** — сучасного асинхронного Python-фреймворку. Головними критеріями вибору були нативна підтримка `async/await`, автоматична генерація OpenAPI-документації на основі анотацій типів та вбудована інтеграція з Pydantic для валідації вхідних і вихідних даних. FastAPI за своєю природою орієнтований на розробку API-first застосунків, що повністю відповідає призначенню платформи.

Як сервер застосунку використовується **Uvicorn** — легковісний ASGI-сервер, що забезпечує обробку асинхронних HTTP-запитів. У виробничому режимі рекомендується запускати його за зворотним проксі-сервером (наприклад, Nginx), однак для цілей розробки Uvicorn є достатнім.

Для роботи з базою даних обрано зв'язку **PostgreSQL + SQLAlchemy 2.x + asyncpg**. PostgreSQL є реляційною СУБД з широкими можливостями — зокрема, нативна підтримка масивів (`ARRAY(String)`) використовується для зберігання тегів транзакцій без потреби у проміжній таблиці. SQLAlchemy надає ORM-шар, що дозволяє описувати структуру даних на рівні Python-класів і виконувати асинхронні запити через `AsyncSession`. Драйвер asyncpg реалізує протокол PostgreSQL у повністю асинхронному режимі без блокування циклу подій.

Для версіонування схеми бази даних застосовується **Alembic** — стандартний інструмент міграцій для SQLAlchemy. Кожна змінна структури таблиць оформлена як окрема ревізія з унікальним ідентифікатором, що дозволяє як накочувати (`upgrade`), так і відкочувати (`downgrade`) схему до будь-якого попереднього стану.

Вся валідація даних на вході та виході побудована на **Pydantic v2**. Схеми запитів і відповідей описані у файлах `schemas.py` кожного функціонального модуля. Pydantic забезпечує автоматичне перетворення типів, генерацію зрозумілих повідомлень про помилки та серіалізацію ORM-об'єктів через режим `from_attributes=True`.

Автентифікація реалізована на основі **JWT-токенів** із використанням двох бібліотек з чітко розподіленими відповідальностями. Бібліотека **PyJWT** відповідає за асинхронне _створення_ токенів, а **python-jose** — за їх синхронне _декодування та верифікацію_ під час обробки запитів. Хешування паролів покладено на **passlib** з алгоритмом bcrypt — він є свідомо повільним і стійким до атак грубою силою.

Соціальна автентифікація через Google та GitHub реалізована за допомогою **authlib** — бібліотеки, що реалізує протокол OAuth2 Authorization Code Flow та OpenID Connect Discovery. Для підтримки серверних сесій, необхідних у OAuth2-потоці, до застосунку підключено `SessionMiddleware` зі Starlette.

Двофакторна автентифікація базується на протоколі TOTP (RFC 6238) через бібліотеку **pyotp**, яка генерує та верифікує одноразові коди. QR-коди для налаштування автентифікатора будуються бібліотекою **qrcode** і повертаються клієнту у вигляді Base64-рядка прямо у тілі JSON-відповіді.

Завантажені файли чеків обробляються різними інструментами залежно від формату. Для PDF-документів текст витягується бібліотекою **pdfplumber**, яка не потребує зовнішніх системних залежностей. Для растрових зображень (JPEG, PNG та інші) використовується **Pillow** для попередньої обробки та **pytesseract** як Python-обгортка над рушієм **Tesseract OCR** — зовнішньою системною програмою. Запис та читання файлів з диску виконується через **aiofiles**, що забезпечує неблокувальний ввід-вивід у асинхронному контексті.

Масовий імпорт транзакцій із таблиць Excel забезпечується бібліотекою **openpyxl**, яка є м'якою залежністю: якщо вона не встановлена, CSV-імпорт продовжує працювати, а спроба завантажити `.xlsx` повертає `501 Not Implemented`. CSV-файли обробляються стандартним модулем `csv` із Python stdlib без жодних додаткових залежностей.

Для виконання HTTP-запитів до зовнішніх сервісів — API Національного банку України, Have I Been Pwned для перевірки паролів та провайдерів OAuth — використовується **httpx**, асинхронний HTTP-клієнт, сумісний з `async/await`.

Гнучке розпізнавання дат під час імпорту транзакцій покладено на **python-dateutil**: ця бібліотека розуміє десятки форматів дати та часу і коректно обробляє часові пояси, звільняючи від потреби описувати кожен формат вручну. Просування `next_run` для щомісячних та щорічних рекурентних транзакцій виконується через **relativedelta** з тієї ж бібліотеки, оскільки звичайний `timedelta` не вміє коректно обробляти межі місяців.

Фонові задачі — оновлення курсів валют та запуск рекурентних транзакцій — реалізовано через декоратор `@repeat_every` з бібліотеки **fastapi-utilities**, що дозволяє реєструвати cron-подібні завдання безпосередньо у процесі запуску FastAPI-застосунку без необхідності підключення окремого планувальника задач на кшталт Celery.

### Обґрунтування вибору ключових компонентів

При формуванні технологічного стеку кожен ключовий компонент розглядався у порівнянні з альтернативними рішеннями. Нижче наведено обґрунтування для трьох найвагоміших виборів.

**Вебфреймворк: FastAPI проти Django REST Framework та Flask.** Django REST Framework пропонує широкий набір вбудованих інструментів — ORM, адміністративну панель, систему автентифікації — однак є синхронним за замовчуванням і несе значний накладний ресурс для проекту, що є виключно RESTful API-сервісом без потреби у рендерингу шаблонів. Крім того, вбудований ORM Django не сумісний з асинхронною моделлю виконання, що ускладнює повноцінне використання `async/await`. Flask у поєднанні з Flask-RESTful є мінімалістичним рішенням, однак потребує ручного підключення та налаштування практично кожного компонента — валідації, серіалізації, автоматичної документації, що значно збільшує обсяг бойлерплейт-коду. FastAPI усуває ці недоліки: нативна підтримка `async/await` забезпечує ефективне використання одного процесу для обробки великої кількості одночасних з'єднань, автоматична генерація OpenAPI-документації виключає необхідність її ручного супроводу, а вбудована інтеграція з Pydantic дозволяє описувати контракти API безпосередньо в анотаціях типів.

**СУБД: PostgreSQL проти MongoDB та MySQL.** MongoDB є документо-орієнтованою СУБД з гнучкими схемами, що є перевагою для прототипування, однак слабші гарантії ACID та відсутність нативної підтримки зовнішніх ключів і JOIN-операцій ускладнюють реалізацію складних реляційних зв'язків між сутностями, наявних у системі: User → Transaction → Receipt, Budget → BudgetMember тощо. MySQL є надійною реляційною СУБД, проте не підтримує нативний тип масивів, що потребувало б виокремлення тегів транзакцій у окрему таблицю та ускладнення запитів із фільтрацією. PostgreSQL поєднує повні ACID-гарантії з розширеними типами даних: нативний тип `ARRAY` дозволяє зберігати теги безпосередньо в рядку транзакції, підтримка `INSERT ... ON CONFLICT DO UPDATE` (upsert) використовується для ефективного оновлення курсів валют, а тип `JSON` забезпечує гнучке зберігання результатів OCR без фіксованої схеми.

**Механізм автентифікації: JWT проти серверних сесій.** Автентифікація на основі серверних сесій передбачає зберігання ідентифікатора сесії у спільному сховищі (зазвичай Redis або таблиця БД), що дозволяє миттєво анулювати сесію на стороні сервера. Однак такий підхід ускладнює горизонтальне масштабування: усі екземпляри сервісу мають поділяти спільне сховище стану. JWT-токени є stateless — сервер не зберігає жодного стану між запитами, оскільки уся необхідна інформація (ідентифікатор користувача, тип токена, термін дії) закодована безпосередньо у токені та підписана симетричним ключем. Це суттєво спрощує масштабування та розгортання. Компромісом є неможливість миттєвої інвалідації виданого токена без додаткового Redis-сховища з чорним списком, що позначено у коді як технічний борг і підлягає реалізації у подальших ітераціях розробки.

## 1.2 Архітектура серверної частини

### 1.2.1 Загальна структура та потік запитів

Серверна частина платформи побудована за принципом **шаруватої архітектури** (layered architecture), де кожен шар має чітко визначену відповідальність і взаємодіє виключно з суміжними шарами. Це забезпечує розділення логіки обробки HTTP-запитів, бізнес-логіки та роботи з базою даних, спрощує підтримку та масштабування системи.

Точкою входу застосунку є файл `src/app.py`, в якому ініціалізується екземпляр FastAPI-застосунку, підключаються всі маршрутизатори (routers) та реєструються компоненти проміжного програмного забезпечення (middleware).

**Ланцюжок обробки HTTP-запиту** проходить через кілька шарів:

```
HTTP-запит
    │
    ▼
┌─────────────────────────────┐
│   CORSMiddleware            │  Перевірка дозволених джерел (origins)
│   SessionMiddleware         │  Підтримка серверних сесій (OAuth2-flow)
│   TimingMiddleware          │  Додає заголовок X-Process-Time до відповіді
└─────────────────────────────┘
    │
    ▼
┌─────────────────────────────┐
│   FastAPI Router            │  Маршрутизація до конкретного обробника
│   /api/*  або  /health      │
└─────────────────────────────┘
    │
    ▼
┌─────────────────────────────┐
│   Dependency Injection      │
│   ├── get_db()              │  Відкриває асинхронну сесію БД
│   └── get_current_user()    │  Валідує Bearer-токен, повертає об'єкт User
└─────────────────────────────┘
    │
    ▼
┌─────────────────────────────┐
│   Route Handler             │  Виконує бізнес-логіку
│   (функція-обробник)        │
└─────────────────────────────┘
    │
    ▼
┌─────────────────────────────┐
│   SQLAlchemy ORM            │  Асинхронні запити до PostgreSQL
└─────────────────────────────┘
    │
    ▼
HTTP-відповідь (JSON)
```

**Middleware.** До застосунку підключено три компоненти проміжного рівня. `CORSMiddleware` відповідає за обробку міжсайтових запитів (CORS) і дозволяє звернення з фронтенд-клієнтів, що працюють на `localhost:3000` та `localhost:5173`. `SessionMiddleware` від бібліотеки Starlette забезпечує підтримку серверних сесій, які необхідні для реалізації OAuth2-потоку з провайдерами Google та GitHub. Власний `TimingMiddleware` вимірює час виконання кожного запиту і додає його значення до заголовка відповіді `X-Process-Time`, що спрощує моніторинг продуктивності під час розробки.

**Dependency Injection.** FastAPI реалізує механізм впровадження залежностей (Dependency Injection) через параметри функцій-обробників із декоратором `Depends`. У системі визначено дві ключові залежності. Перша — `get_db()` — реалізована як асинхронний генератор, що відкриває нову сесію `AsyncSession` з пулу з'єднань бібліотеки SQLAlchemy та автоматично закриває її після завершення запиту. Друга — `get_current_user()` — виконує автентифікацію: витягує Bearer-токен із заголовка `Authorization`, декодує його за допомогою `python-jose`, перевіряє тип токена і термін його дії, після чого завантажує відповідний об'єкт `User` з бази даних. У разі будь-якої невідповідності повертається відповідь зі статусом `401 Unauthorized`. Переважна більшість захищених ендпоінтів оголошує обидві залежності одночасно.

**Фонові задачі (Cron-jobs).** Окрім обробки HTTP-запитів, застосунок виконує дві фонові задачі, що реєструються під час запуску через функції `register_currency_cron()` та `register_recurring_cron()`. Перша щогодини отримує актуальні курси валют від API Національного банку України і оновлює їх у таблиці `currencies`. Друга запускається щохвилини, перевіряє рекурентні транзакції з терміном `next_run ≤ now` і автоматично створює відповідні записи у таблиці `transactions`, після чого просуває `next_run` на один кроковий інтервал.

Такий підхід до організації серверної частини дозволяє чітко відокремити транспортний рівень (HTTP, middleware) від рівня застосунку (бізнес-логіка в обробниках) та рівня даних (SQLAlchemy + PostgreSQL), що відповідає принципу єдиної відповідальності та забезпечує зручність подальшого розширення системи.

### 1.2.2 Структура модулів проекту

Кодова база серверної частини організована за принципом **функціональної декомпозиції** (feature-based structure): кожен самостійний функціональний домен виокремлено в окремий пакет всередині директорії `src/`. Такий підхід дозволяє локалізувати всі зміни, пов'язані з певною функціональністю, в межах одного модуля — без необхідності вносити правки у спільні файли.

Верхній рівень `src/` містить кілька базових файлів, що забезпечують роботу всього застосунку:

| Файл | Призначення |
|---|---|
| `app.py` | Точка входу: ініціалізація FastAPI, підключення middleware та маршрутизаторів |
| `config.py` | Зчитування змінних оточення (`.env`), налаштування логування |
| `database.py` | Асинхронний рушій SQLAlchemy, фабрика сесій `AsyncSessionLocal`, базовий клас `Base` |
| `dependencies.py` | Спільні залежності FastAPI: `get_db()`, `get_current_user()` |
| `models.py` | Усі ORM-моделі проекту в одному файлі |
| `security.py` | Допоміжні функції безпеки (використовуються у dependencies) |

Функціональні модулі розміщено у власних піддиректоріях і дотримуються єдиної внутрішньої структури:

```
src/<module>/
    __init__.py
    <module>_router.py   ← FastAPI-маршрутизатор з обробниками ендпоінтів
    schemas.py           ← Pydantic-схеми запитів та відповідей
    services/            ← (за потреби) сервісна логіка, винесена з роутера
```

Нижче наведено перелік усіх функціональних модулів та їх призначення:

| Модуль | URL-префікс | Опис |
|---|---|---|
| `auth/` | `/api/auth` | Реєстрація, вхід, хешування паролів, валідація надійності пароля |
| `transactions/` | `/api/transactions` | CRUD-операції з транзакціями; також містить `recurring_router.py`, `import_router.py` та `currency_converter.py` |
| `budgets/` | `/api/budgets` | Управління бюджетами та учасниками бюджету |
| `analytics/` | `/api/analytics` | Аналітичні звіти; логіку винесено у `services/` (огляд, тренди, категорії, порівняння бюджетів) |
| `goals/` | `/api/goals` | Управління фінансовими цілями (накопичувальні «банки») |
| `users/` | `/api/users` | Перегляд та редагування профілю, видалення акаунту |
| `currencies/` | `/api/currencies` | Читання курсів валют; cron-задача оновлення від API НБУ |
| `settings/` | `/api/settings` | Налаштування профілю, валюти, email, сповіщень та підписки |
| `files/` | `/api/files` | Завантаження файлів-чеків, OCR-аналіз, зв'язування з транзакціями; сервіси — у `services/` |
| `two_fa/` | `/api/2fa` | Налаштування та перевірка TOTP-двофакторної автентифікації |
| `google_oauth/` | `/api/auth/google` | OAuth2-автентифікація через Google |
| `github_oauth/` | `/api/auth/github` | OAuth2-автентифікація через GitHub |
| `health/` | `/health` | Ендпоінт перевірки доступності сервісу |
| `for_testing/` | `/api/dev` | Ендпоінт без автентифікації для заповнення БД тестовими даними |

Окремо виділено директорію `utils/`, яка містить допоміжні утиліти, що використовуються різними модулями:

| Файл | Призначення |
|---|---|
| `jwt_handlers.py` | Асинхронне **створення** JWT-токенів на основі бібліотеки `PyJWT` |
| `security.py` | Синхронне **декодування** та верифікація токенів на основі `python-jose` |
| `auth_services.py` | Хешування паролів (`pbkdf2_sha256`), перевірка пароля, автентифікація користувача |
| `getters_services.py` | Допоміжні функції вибірки користувача з БД за email або id |
| `exceptions.py` | Визначення стандартних HTTP-виключень, що повторно використовуються у різних роутерах |

Варто зазначити, що модуль `transactions/` має дещо ширший обсяг порівняно з іншими: окрім основного маршрутизатора, він включає три додаткових компоненти. `recurring_router.py` обслуговує рекурентні транзакції та реєструє відповідну cron-задачу. `import_router.py` забезпечує масовий імпорт транзакцій з файлів CSV та Excel. `currency_converter.py` реалізує логіку конвертації суми транзакції з валюти джерела до валюти за замовчуванням користувача через USD як проміжну одиницю. Аналогічно, модуль `analytics/` виносить усю обчислювальну логіку у підпакет `services/`, де кожен аналітичний звіт реалізовано окремим сервісним файлом — `overview_service.py`, `trends_service.py`, `category_service.py`, `budget_comparison_service.py` та інші.

Така організація коду забезпечує **низьке зчеплення** між модулями та **високу зв'язність** всередині кожного з них, що є основним критерієм якісної архітектури програмного забезпечення.

### 1.2.3 Модель бази даних

База даних системи побудована на основі реляційної СУБД PostgreSQL і налічує **дев'ять таблиць** та **сім перечислень** (enum-типів). Усі ORM-моделі зосереджено в єдиному файлі `src/models.py` та успадковують декларативний базовий клас `Base` з SQLAlchemy. Первинний ключ у кожній таблиці має ім'я `id_` (з підкресленням) — це свідоме рішення, що дозволяє уникнути конфліктів із вбудованою функцією Python `id()`. Усі поля дати та часу зберігаються з інформацією про часовий пояс (`timezone=True`), серверне значення за замовчуванням обчислюється через `func.now()` та відповідає моменту виконання SQL-запиту.

#### Перечислення

Перед описом таблиць наведено перелік усіх enum-типів, які використовуються як типи стовпців.

`UserStatus` розрізняє рядових користувачів (`USER = 0`) та адміністраторів системи (`ADMIN = 1`). `TransactionKind` визначає три типи фінансових операцій: витрата (`EXPENSE = 0`), дохід (`INCOME = 1`) та переказ між рахунками (`TRANSFER = 2`). `Currencies` містить десять ISO-4217-кодів підтримуваних валют: `USD`, `EUR`, `JPY`, `GBP`, `AUD`, `CHF`, `SEK`, `NOK`, `PLN`, `UAH`. `BudgetType` визначає призначення бюджету: `PERSONAL` — особистий, `FAMILY` — сімейний, `BUSINESS` — бізнесовий. `BudgetRole` описує роль учасника бюджету: `OWNER` — власник, `EDITOR` — редактор, `VIEWER` — спостерігач. `RecurringFrequency` задає частоту повторення транзакції: `DAILY`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`, `YEARLY`. `SubscriptionPlan` розрізняє два рівні підписки: `FREE` та `PRO`.

#### Таблиця `users`

Центральна сутність системи. Зберігає облікові дані, налаштування та агрегований фінансовий стан кожного зареєстрованого користувача. Усі інші таблиці посилаються на `users` через зовнішній ключ.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | — | Унікальний числовий ідентифікатор |
| `username` | `String(64)` | NOT NULL, UNIQUE | — | Ім'я користувача у системі |
| `email` | `String(255)` | NOT NULL, UNIQUE | — | Електронна адреса |
| `hashed_password` | `String(255)` | NOT NULL | — | Хеш пароля (bcrypt через passlib); для OAuth-акаунтів містить службову заглушку |
| `default_currency` | `String(3)` | NOT NULL, CHECK | `USD` | Валюта за замовчуванням; перевіряється на рівні БД |
| `timezone` | `String(64)` | NULL | `NULL` | IANA-ідентифікатор часового поясу |
| `capital` | `Float` | NOT NULL | `0.0` | Денормалізований агрегований баланс у валюті за замовчуванням |
| `role` | `Enum(UserStatus)` | NOT NULL | `USER` | Системна роль |
| `twofa_secret` | `String(32)` | NULL | `NULL` | Base32-секрет TOTP; `NULL` до першого налаштування 2FA |
| `twofa_enabled` | `Boolean` | NOT NULL | `False` | Прапорець активації двофакторної автентифікації |
| `avatar_url` | `String(512)` | NULL | `NULL` | URL аватара користувача |
| `subscription_plan` | `Enum(SubscriptionPlan)` | NOT NULL | `FREE` | Поточний план підписки |

**Обмеження рівня БД:** `CHECK (default_currency IN ('USD','EUR','JPY','GBP','AUD','CHF','SEK','NOK','PLN','UAH'))` — запобігає запису довільного коду валюти в обхід ORM.

Поле `capital` є свідомо денормалізованим: воно дублює інформацію, яку теоретично можна обчислити як суму всіх транзакцій. Таке рішення прийнято з міркувань продуктивності — уникнення агрегувального запиту по всій таблиці транзакцій при кожному зверненні до балансу. Цілісність `capital` підтримується на рівні застосунку: кожна операція запису або видалення транзакції атомарно коригує це поле.

#### Таблиця `currencies`

Зберігає актуальні обмінні курси валют відносно долара США. Таблиця є довідниковою і не має зовнішніх ключів до інших сутностей.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `name` | `String(16)` | PK | — | ISO-4217-код валюти, наприклад `USD`, `EUR`, `UAH` |
| `rate` | `Float` | NOT NULL | `1.0` | Кількість одиниць цієї валюти, еквівалентна одному долару США |

Первинним ключем є рядковий код валюти, що природньо усуває дублікати. Курс USD завжди дорівнює `1.0` і слугує опорною точкою для конвертації. Таблиця оновлюється щогодини cron-задачею через upsert (`INSERT ... ON CONFLICT DO UPDATE`).

#### Таблиця `transactions`

Основна операційна таблиця системи. Кожен рядок представляє одну фінансову операцію користувача — витрату, дохід або переказ.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement, index | — | Унікальний ідентифікатор транзакції |
| `user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL | — | Власник транзакції |
| `amount` | `Numeric(14, 2)` | NOT NULL | — | Сума; тип `Numeric` усуває похибки представлення з плаваючою комою |
| `name` | `String(64)` | NOT NULL | `""` | Назва або короткий опис операції |
| `kind` | `Enum(TransactionKind)` | NOT NULL | `EXPENSE` | Тип операції |
| `category_name` | `String(64)` | NOT NULL | — | Категорія; зберігається у нижньому регістрі; перевіряється на рівні застосунку |
| `currency` | `String(16)` | NULL | `NULL` | Валюта операції; якщо `NULL`, застосовується `default_currency` користувача |
| `tags` | `ARRAY(String)` | NOT NULL | `{}` | Масив тегів; нормалізуються до нижнього регістру |
| `note` | `String(512)` | NULL | `NULL` | Довільний коментар |
| `date` | `DateTime(tz)` | NOT NULL | `now()` | Дата та час операції; може бути передана клієнтом або виставлена сервером |

**Тип `ARRAY(String)`** є PostgreSQL-розширенням і дозволяє зберігати теги безпосередньо у рядку без потреби у проміжній таблиці `transaction_tags`. Фільтрація за тегом виконується через оператор `contains`: `Transaction.tags.contains([tag])`.

**Каскадне видалення** (`ondelete="CASCADE"`) гарантує, що при видаленні користувача всі його транзакції автоматично видаляються без потреби у явних запитах на рівні застосунку.

#### Таблиця `goals`

Зберігає фінансові цілі користувача — накопичувальні «банки» з цільовою сумою, прогресом і необов'язковим дедлайном.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | — | Ідентифікатор |
| `user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL, index | — | Власник цілі |
| `name` | `String(255)` | NOT NULL | — | Назва цілі |
| `target_amount` | `Numeric(14, 2)` | NOT NULL | — | Цільова сума накопичення |
| `saved_amount` | `Numeric(14, 2)` | NOT NULL | `0` | Поточна накопичена сума |
| `currency` | `String(3)` | NOT NULL | `USD` | Валюта цілі |
| `description` | `String(512)` | NULL | `NULL` | Необов'язковий опис |
| `deadline` | `DateTime(tz)` | NULL | `NULL` | Бажана дата досягнення |
| `is_completed` | `Boolean` | NOT NULL | `False` | Прапорець завершення |
| `completed_at` | `DateTime(tz)` | NULL | `NULL` | Момент завершення; `NULL` поки ціль активна |
| `created_at` | `DateTime(tz)` | NOT NULL | `now()` | Дата створення |

Пара полів `is_completed` / `completed_at` утворює стан завершення з часовою міткою. Їх розділення принципове: `completed_at` дозволяє зберегти інформацію про те, коли саме ціль була досягнута, навіть якщо вона згодом була перевідкрита. Обчислювальне поле `progress_percent` не зберігається у БД, а розраховується динамічно Pydantic-схемою відповіді.

| Стовпець | Тип | Обмеження | Опис |

#### Таблиця `budgets`

Представляє бюджет — іменований фінансовий контейнер із необов'язковим лімітом витрат. Бюджет завжди має одного власника і може мати додаткових учасників через таблицю `budget_members`.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | — | Ідентифікатор |
| `owner_user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL, index | — | Власник бюджету |
| `name` | `String(128)` | NOT NULL | — | Назва бюджету |
| `type` | `Enum(BudgetType)` | NOT NULL | — | Тип: особистий, сімейний або бізнесовий |
| `currency` | `String(3)` | NOT NULL, CHECK | `USD` | Валюта бюджету |
| `limit_amount` | `Numeric(14, 2)` | NULL | `NULL` | Необов'язковий ліміт витрат для аналітики |
| `created_at` | `DateTime(tz)` | NOT NULL | `now()` | Дата створення |

**Обмеження рівня БД:** `CHECK (currency IN ('USD','EUR','JPY','GBP','AUD','CHF','SEK','NOK','PLN','UAH'))` — аналогічно до таблиці `users`.

Поле `limit_amount` є необов'язковим і не контролюється автоматично системою. Воно використовується виключно аналітичним сервісом `BudgetComparisonService` для порівняння фактичних витрат із запланованими.

#### Таблиця `budget_members`

Реалізує зв'язок «багато-до-багатьох» між користувачами та бюджетами з додатковим атрибутом ролі. Кожен рядок описує участь конкретного користувача у конкретному бюджеті.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | — | Ідентифікатор запису членства |
| `budget_id` | `Integer` | FK → `budgets.id_`, CASCADE, NOT NULL, index | — | Бюджет |
| `user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL, index | — | Учасник |
| `role` | `Enum(BudgetRole)` | NOT NULL | `VIEWER` | Роль учасника у бюджеті |

**Унікальне обмеження:** `UNIQUE (budget_id, user_id)` — один користувач не може бути доданий до одного бюджету двічі, що контролюється на рівні бази даних і повертає `409 Conflict` на рівні застосунку.

При створенні бюджету власник автоматично додається до цієї таблиці з роллю `OWNER`. Список бюджетів поточного користувача формується через `JOIN` з цією таблицею, що однаково охоплює як власні бюджети, так і бюджети, до яких він запрошений.

#### Таблиця `recurring_transactions`

Зберігає правила автоматичного повторення транзакцій. Кожен рядок є шаблоном, за яким cron-задача створює реальні транзакції у таблиці `transactions` у заданий момент часу.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | — | Ідентифікатор правила |
| `user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL, index | — | Власник правила |
| `name` | `String(64)` | NOT NULL | — | Назва правила |
| `amount` | `Numeric(14, 2)` | NOT NULL | — | Сума кожного спрацювання |
| `kind` | `Enum(TransactionKind)` | NOT NULL | `EXPENSE` | Тип транзакції |
| `category_name` | `String(64)` | NOT NULL | — | Категорія (ті самі правила, що і в `transactions`) |
| `currency` | `String(16)` | NULL | `NULL` | Валюта; якщо `NULL`, використовується `default_currency` |
| `tags` | `ARRAY(String)` | NOT NULL | `{}` | Теги, що передаються породженій транзакції |
| `note` | `String(512)` | NULL | `NULL` | Нотатка |
| `frequency` | `Enum(RecurringFrequency)` | NOT NULL | — | Частота повторення |
| `next_run` | `DateTime(tz)` | NOT NULL | — | Момент наступного спрацювання; cron-задача відбирає записи за умовою `next_run ≤ now()` |
| `is_active` | `Boolean` | NOT NULL | `True` | Прапорець активності; `False` призупиняє правило без видалення |
| `created_at` | `DateTime(tz)` | NOT NULL | `now()` | Дата створення правила |

Таблиця навмисно не містить зовнішнього ключа на `transactions` — правило і породжені ним транзакції пов'язані логічно, але не реляційно, щоб видалення правила не каскадно видаляло вже зафіксовані операції.

#### Таблиця `notification_preferences`

Зберігає налаштування каналів та типів сповіщень для конкретного користувача. Таблиця знаходиться у відношенні **один-до-одного** з `users`: один запис відповідає одному користувачу, що забезпечується `UNIQUE`-обмеженням на `user_id`.

| Стовпець | Тип | Обмеження | Значення за замовч. | Опис |
|---|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | — | Ідентифікатор |
| `user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL, UNIQUE | — | Власник налаштувань (1:1 з `users`) |
| `email_enabled` | `Boolean` | NOT NULL | `True` | Канал: надсилання на email |
| `push_enabled` | `Boolean` | NOT NULL | `False` | Канал: push-сповіщення |
| `budget_limit_alerts` | `Boolean` | NOT NULL | `True` | Подія: наближення до ліміту бюджету |
| `recurring_reminders` | `Boolean` | NOT NULL | `True` | Подія: нагадування перед рекурентною транзакцією |
| `goal_milestone_alerts` | `Boolean` | NOT NULL | `True` | Подія: досягнення проміжної позначки цілі |
| `monthly_summary` | `Boolean` | NOT NULL | `True` | Подія: місячний підсумковий дайджест |

Запис у цій таблиці **не створюється при реєстрації** — він ліниво ініціалізується з наведеними значеннями за замовчуванням при першому зверненні до ендпоінту `GET /api/settings/notifications`.

---

#### Таблиця `receipts`

Зберігає метадані завантажених файлів-чеків та результати їх OCR-аналізу. Файл фізично розміщується на диску, а в таблиці зберігається лише інформація про нього.

| Стовпець | Тип | Обмеження | Опис |
|---|---|---|---|
| `id_` | `Integer` | PK, autoincrement | Ідентифікатор |
| `user_id` | `Integer` | FK → `users.id_`, CASCADE, NOT NULL, index | Власник файлу |
| `transaction_id` | `Integer` | FK → `transactions.id_`, SET NULL, NULL, index | Прив'язана транзакція; `NULL` якщо чек не пов'язано |
| `original_filename` | `String(255)` | NOT NULL | Оригінальне ім'я файлу, надане клієнтом |
| `stored_filename` | `String(255)` | NOT NULL | UUID-ім'я файлу на диску; унеможливлює атаки через підбір шляху |
| `file_path` | `String(512)` | NOT NULL | Відносний шлях усередині `UPLOAD_DIR`, наприклад `7/a1b2c3.jpg` |
| `content_type` | `String(64)` | NOT NULL | MIME-тип файлу (наприклад, `image/jpeg`, `application/pdf`) |
| `file_size` | `Integer` | NOT NULL | Розмір файлу у байтах |
| `ocr_result` | `JSON` | NULL | Структурований результат OCR-аналізу; `NULL` якщо OCR не виконувався або зазнав збою |
| `created_at` | `DateTime(tz)` | NOT NULL, `now()` | Дата завантаження |

**Стратегія `SET NULL` при видаленні транзакції** є принциповим рішенням: файл-чек залишається у системі навіть якщо транзакція, до якої він був прив'язаний, видалена. Це дозволяє уникнути ненавмисної втрати завантажених документів.

#### Зв'язки між сутностями

Схему зв'язків між таблицями узагальнено нижче. Для кожного зв'язку вказано його тип, спрямованість та поведінку при видаленні батьківського запису.

**Один-до-багатьох** (`User` → дочірні таблиці, усі з `CASCADE DELETE`):
- `users` → `transactions` — користувач має довільну кількість транзакцій
- `users` → `goals` — користувач має довільну кількість фінансових цілей
- `users` → `budgets` (як `owner_user_id`) — користувач є власником довільної кількості бюджетів
- `users` → `recurring_transactions` — користувач має довільну кількість правил повторення
- `users` → `receipts` — користувач має довільну кількість завантажених чеків
- `users` → `notifications` — користувач має довільну кількість нагадувань

**Один-до-одного** (`CASCADE DELETE`):
- `users` → `notification_preferences` — кожному користувачу відповідає рівно один запис налаштувань сповіщень (зв'язок забезпечується `UNIQUE (user_id)` у таблиці `notification_preferences`)

**Багато-до-багатьох** з атрибутом (через асоціативну таблицю):
- `users` ↔ `budgets` через `budget_members` — один користувач може бути учасником багатьох бюджетів, один бюджет може мати багатьох учасників; кожний зв'язок доповнений роллю (`BudgetRole`)

**Один-до-багатьох** між дочірніми таблицями:
- `transactions` → `receipts` — одна транзакція може мати кілька прикріплених чеків; при видаленні транзакції `transaction_id` у `receipts` встановлюється у `NULL` (`SET NULL`), сам файл зберігається

**Відсутній явний зв'язок:**
- `recurring_transactions` та `transactions` не пов'язані зовнішнім ключем навмисно: породжені транзакції зберігають незалежне існування після спрацювання правила.

## 1.3 Безпека та автентифікація

### 1.3.1 Реєстрація та вхід — JWT-токени

Автентифікація в системі базується на механізмі **JWT-токенів** (JSON Web Token). Після успішного входу або реєстрації клієнт отримує пару токенів — короткоживучий `access_token` для доступу до захищених ресурсів та довгоживучий `refresh_token` для його оновлення без повторного введення пароля. Усі ендпоінти автентифікації розміщено за префіксом `/api/auth`.

#### Реєстрація

Реєстрація нового користувача виконується через ендпоінт `POST /api/auth/signup`. Тіло запиту повинне містити три поля:

| Поле | Тип | Обмеження |
|---|---|---|
| `username` | `string` | Від 3 до 64 символів; унікальний в системі |
| `email` | `string` | Валідна email-адреса (перевіряється через `EmailStr`); унікальна в системі |
| `password` | `string` | Мінімум 8 символів; проходить розширену перевірку надійності |

Перед створенням запису сервер послідовно виконує такі перевірки:

**1. Унікальність.** Система перевіряє, чи не зайнято вже вказаний `email` та `username`. У разі конфлікту повертається відповідь зі статусом `400 Bad Request` та відповідним повідомленням.

**2. Надійність пароля.** Пароль перевіряється за п'ятьма правилами одночасно:
- наявність щонайменше однієї великої літери;
- наявність щонайменше однієї малої літери;
- наявність щонайменше однієї цифри;
- наявність щонайменше одного спеціального символу з набору `@$!%*?&`;
- пароль не входить до двох словників поширених паролів, що зберігаються локально (`500-worst-passwords.txt` та `Pwdb_top-1000.txt`, загалом близько 1500 записів).

**3. Перевірка витоків (HIBP).** Додатково система асинхронно звертається до публічного API сервісу **Have I Been Pwned** за схемою k-анонімності: обчислюється SHA-1 хеш пароля, перші 5 символів надсилаються на `api.pwnedpasswords.com/range/{prefix}`, після чого відповідь порівнюється з хвостовою частиною хешу. Якщо збіг знайдено — пароль фігурує у відомих витоках даних і реєстрація блокується. Оскільки перевіряється лише префікс, оригінальний пароль жодного разу не залишає сервер. Якщо сервіс HIBP недоступний, перевірка мовчки пропускається — реєстрація не блокується.

За умови успішного проходження всіх перевірок пароль хешується алгоритмом **PBKDF2-SHA256** за допомогою бібліотеки `passlib`, після чого новий запис зберігається у таблиці `users` з початковим значенням балансу `capital = 0.0`. У відповідь клієнт отримує готову пару токенів — реєстрація та вхід об'єднані в одну дію.

#### Вхід

Вхід до системи здійснюється через ендпоінт `POST /api/auth/login`. Тіло запиту містить `email` та `password`. Email автоматично приводиться до нижнього регістру перед пошуком у базі даних. Якщо користувача з вказаним email не знайдено або пароль не відповідає збереженому хешу, повертається відповідь `401 Unauthorized` з узагальненим повідомленням `"Invalid credentials"` — без уточнення, яке саме поле є невірним, що унеможливлює атаки на перебір.

Якщо для акаунта увімкнено двофакторну автентифікацію, стандартний потік входу переривається: замість повноцінних токенів клієнт отримує тимчасовий `temp_token` типу `2fa_pending` з терміном дії **5 хвилин** та прапорець `requires_2fa: true`. Далі клієнт має передати цей токен разом із TOTP-кодом на ендпоінт `POST /api/auth/2fa/complete` для завершення входу. Цей механізм детально описано в підрозділі 1.3.3.

#### Структура та термін дії JWT-токенів

Кожен виданий токен є підписаним JWT, що містить три поля у payload:

| Поле | Значення |
|---|---|
| `sub` | Ідентифікатор користувача (рядок) |
| `exp` | Unix-timestamp закінчення дії токена |
| `type` | Тип: `"access"`, `"refresh"` або `"2fa_pending"` |

Токени підписуються симетричним ключем `SECRET_KEY` алгоритмом, що задається змінною оточення `ALGORITHM` (за замовчуванням `HS256`). Термін дії кожного типу токена задається окремими змінними оточення: `ACCESS_TOKEN_EXPIRE_MINUTES` для access-токена та `REFRESH_TOKEN_EXPIRE_DAYS` для refresh-токена. Для **створення** токенів використовується бібліотека `PyJWT`, тоді як для **декодування та верифікації** під час обробки запитів — `python-jose`. Розділення цих двох операцій між різними бібліотеками є свідомим архітектурним рішенням, і ці дві бібліотеки не перетинаються в межах одного модуля.

Поле `type` використовується як додатковий захист: access-токен не можна передати як refresh і навпаки. Спроба використати `refresh`- або `2fa_pending`-токен для доступу до захищених ендпоінтів повертає `401 Unauthorized`.

#### Оновлення токена

Ендпоінт `POST /api/auth/refresh` приймає дійсний `refresh_token` та повертає нову пару `access_token` + `refresh_token` — тобто реалізовано **ротацію refresh-токенів**. Це означає, що кожен refresh-токен може бути використаний лише один раз: після оновлення клієнт зобов'язаний зберегти новий refresh-токен і відкинути старий.

#### Вихід із системи

Вихід реалізовано через ендпоінт `POST /api/auth/logout`. Оскільки JWT-токени є stateless та не зберігаються на сервері, серверна сторона не може їх анулювати. Ендпоінт лише повідомляє клієнту відкинути обидва токени. Повноцінна серверна інвалідація токенів (через чорний список на базі Redis) позначена у коді як `TODO`.

#### Зміна пароля

Змінити пароль можна через ендпоінт `PATCH /api/auth/password` (вимагає автентифікації). Запит повинен містити `current_password` для підтвердження особи та `new_password`, до якого застосовуються ті самі правила надійності, що й під час реєстрації.

### 1.3.2 Соціальна автентифікація — Google OAuth2 та GitHub OAuth2

Окрім класичного входу за email і паролем, система підтримує автентифікацію через зовнішні провайдери — **Google** та **GitHub**. Обидва варіанти реалізовані за стандартним протоколом **OAuth2 Authorization Code Flow** з використанням бібліотеки `authlib`. Ендпоінти Google розміщено за префіксом `/api/auth/google`, GitHub — `/api/auth/github`.

Для роботи OAuth2-потоку необхідна підтримка серверних сесій — саме для цього до застосунку підключено `SessionMiddleware` (описано у підрозділі 1.2.1): бібліотека `authlib` зберігає у сесії тимчасовий `state`-параметр для захисту від CSRF-атак.

#### Загальна схема потоку

Обидва провайдери дотримуються однакової послідовності кроків:

```
Клієнт                        Сервер                        Провайдер (Google / GitHub)
   │                              │                                      │
   │  GET /auth/{provider}/login  │                                      │
   │─────────────────────────────>│                                      │
   │                              │── redirect_uri, state ──────────────>│
   │<─── 302 redirect ────────────│                                      │
   │                              │                            Користувач надає дозвіл
   │                              │<──── code, state ───────────────────│
   │                              │  GET /auth/{provider}/callback       │
   │                              │── обмін code на access_token ───────>│
   │                              │<──── userinfo ──────────────────────│
   │                              │  пошук / створення User у БД         │
   │                              │  генерація JWT-пари                  │
   │<── JSON + httponly cookies ──│                                      │
```

#### Автентифікація через Google

Реєстрацію Google-клієнта виконано через механізм **OpenID Connect Discovery**: сервер самостійно завантажує список ендпоінтів провайдера за стандартною URL-адресою `https://accounts.google.com/.well-known/openid-configuration`. Запитувані дозволи (scopes): `openid email profile`.

Після того як користувач надає згоду на сторінці Google, провайдер перенаправляє браузер на `GET /api/auth/google/callback` з одноразовим кодом авторизації. Сервер обмінює цей код на токен доступу та витягує з нього об'єкт `userinfo` з полями `email`, `email_verified`, `name` та `picture`.

Перед продовженням перевіряється обов'язкова умова: `email_verified` має дорівнювати `true`. Якщо Google повертає email, що не підтверджений, запит відхиляється зі статусом `400 Bad Request`.

#### Автентифікація через GitHub

GitHub не реалізує OpenID Connect, тому клієнт зареєстровано вручну із явним зазначенням ендпоінтів провайдера. Запитувані дозволи: `read:user user:email`.

Отримання email-адреси є дещо складнішим процесом: GitHub не завжди включає email у базову відповідь про користувача, тому сервер виконує окремий запит до `GET /user/emails`. З отриманого списку обирається адреса за такою пріоритетністю:
1. email, що позначений як **primary** і **verified**;
2. будь-який інший **verified** email;
3. email із базового профілю `GET /user`.

Якщо жодного підтвердженого email отримати не вдалося — запит відхиляється зі статусом `400 Bad Request`. Ім'я користувача (`username`) береться з поля `login` профілю GitHub.

#### Автоматична реєстрація

Обидва провайдери використовують однакову логіку прив'язки облікового запису. Після отримання email сервер шукає у базі даних запис з такою адресою:

- **Користувач знайдений** — виконується вхід до вже існуючого акаунту; дані з провайдера ігноруються.
- **Користувач не знайдений** — автоматично створюється новий акаунт. Поле `password` заповнюється службовим рядком-заглушкою (`__google_oauth__` або `__github_oauth__`), який не може бути введений користувачем вручну і не відповідає жодному з правил надійності пароля.

Завдяки цьому механізму один і той самий email, незалежно від способу першої реєстрації (форма або OAuth), завжди відповідатиме одному акаунту.

#### Відповідь сервера

Після успішної автентифікації сервер повертає:
- JSON-тіло з `access_token`, `refresh_token`, `user_id`, `email` та даними профілю (ім'я, фото/аватар);
- два `httponly`-cookie — `access_token` та `refresh_token` — для браузерних клієнтів, що не мають змоги зберігати токени вручну.

Токени, що видаються через OAuth, є ідентичними за структурою токенам від звичайного входу і використовуються для доступу до всіх захищених ендпоінтів однаково.

### 1.3.3 Двофакторна автентифікація (TOTP)

Система підтримує двофакторну автентифікацію на основі протоколу **TOTP** (Time-based One-Time Password, RFC 6238). Після її активації кожен вхід вимагає, окрім пароля, шестизначного одноразового коду, що генерується у мобільному застосунку-автентифікаторі (Google Authenticator, Authy тощо). Усі ендпоінти керування 2FA розміщено за префіксом `/api/2fa` і потребують дійсного access-токена.

У базі даних модель `User` містить два поля, що відповідають за стан 2FA:

| Поле | Тип | Опис |
|---|---|---|
| `twofa_secret` | `String(32)` | Base32-секрет TOTP; `null` якщо 2FA ніколи не налаштовувалась |
| `twofa_enabled` | `Boolean` | Прапорець активації; `false` поки код не підтверджено |

Розділення цих двох полів є принциповим: секрет може бути збережений, але 2FA вважається вимкненою доти, доки користувач не підтвердить, що правильно відсканував QR-код.

#### Активація 2FA

Процес налаштування складається з двох кроків.

**Крок 1 — генерація секрету та QR-коду** (`POST /api/2fa/setup`). Сервер перевіряє, що 2FA ще не увімкнена (якщо увімкнена — повертає `409 Conflict`). Далі генерується новий випадковий Base32-секрет за допомогою `pyotp.random_base32()` і зберігається у полі `twofa_secret` без зміни `twofa_enabled`. На основі секрету формується стандартний **OTPAuth URI** такого вигляду:

```
otpauth://totp/FinanceSystem:<email>?secret=<BASE32_SECRET>&issuer=FinanceSystem
```

З цього URI бібліотека `qrcode` будує PNG-зображення, яке кодується у Base64 і повертається клієнту разом із текстовим секретом для ручного введення. Відповідь містить два поля:

| Поле | Опис |
|---|---|
| `qr_code_base64` | PNG QR-коду у форматі Base64 для відображення в інтерфейсі |
| `secret` | Текстовий Base32-секрет для ручного введення в автентифікатор |

Якщо користувач викликав `/setup` повторно, не завершивши підтвердження, секрет перегенерується — попередній анулюється.

**Крок 2 — підтвердження коду** (`POST /api/2fa/verify`). Користувач сканує QR-код застосунком-автентифікатором, отримує перший TOTP-код та надсилає його у полі `code`. Сервер перевіряє його за допомогою `pyotp.TOTP(secret).verify(code)`. При успішній перевірці поле `twofa_enabled` встановлюється у `true` — з цього моменту 2FA активована.

#### Вхід із увімкненою 2FA

Коли користувач намагається увійти через `POST /api/auth/login` і його акаунт має `twofa_enabled = true`, стандартний потік видачі токенів переривається. Замість пари access/refresh-токенів сервер повертає:

```json
{
  "requires_2fa": true,
  "temp_token": "<JWT типу 2fa_pending, термін дії 5 хвилин>"
}
```

Клієнт має відобразити форму введення TOTP-коду і надіслати запит на `POST /api/auth/2fa/complete` з тілом:

| Поле | Опис |
|---|---|
| `temp_token` | Тимчасовий токен, отриманий на попередньому кроці |
| `code` | 6-значний TOTP-код із застосунку-автентифікатора |

Сервер декодує `temp_token`, перевіряє що його тип дорівнює `"2fa_pending"` і що він не прострочений, після чого верифікує TOTP-код. При успіху видається повноцінна пара `access_token` + `refresh_token`. Якщо `temp_token` прострочений або код невірний — повертається `401 Unauthorized`.

П'ятихвилинне часове вікно для завершення другого кроку є свідомо обмеженим з метою мінімізації часового вікна для атак із перехопленим тимчасовим токеном.

#### Деактивація 2FA

Вимкнути 2FA можна через `POST /api/2fa/disable`. Запит потребує поточного дійсного TOTP-коду у полі `code` — це унеможливлює деактивацію зловмисником, який отримав лише access-токен. При успішній перевірці поля `twofa_enabled` та `twofa_secret` обнуляються, і наступний вхід відбувається без двофакторного кроку.

## 1.4 Бізнес-логіка та функціональні можливості

### 1.4.1 Управління транзакціями та категоризація витрат

Транзакції є центральною сутністю платформи — саме вони формують фінансову історію користувача та є основою для аналітики, бюджетування й відстеження цілей. Усі ендпоінти модуля розміщено за префіксом `/api/transactions` і потребують автентифікації.

#### Структура транзакції

Кожна транзакція в системі описується такими полями:

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `name` | `string` | 1–64 символи | Назва або короткий опис |
| `amount` | `Numeric(14, 2)` | ≥ 0 | Сума; зберігається як десятковий тип для уникнення похибок float |
| `kind` | `enum` | EXPENSE / INCOME / TRANSFER | Тип транзакції |
| `category_name` | `string` | з дозволеного списку | Категорія; зберігається у нижньому регістрі |
| `currency` | `string` | ISO-код валюти | Якщо не вказано — використовується валюта за замовчуванням користувача |
| `date` | `datetime` | — | Дата транзакції; якщо не передана — проставляється поточний час сервером |
| `tags` | `string[]` | — | Масив тегів; нормалізуються до нижнього регістру |
| `note` | `string` | до 512 символів | Довільний коментар |

#### Типи та категоризація

Система розрізняє три типи транзакцій, кожен з яких має власний закритий список допустимих категорій. Усі назви зберігаються та порівнюються виключно у нижньому регістрі.

**EXPENSE** (витрати) — 25 категорій:
`shopping`, `food`, `phone`, `entertainment`, `education`, `beauty`, `sports`, `social`, `transportation`, `clothing`, `car`, `alcohol`, `cigarettes`, `electronics`, `travel`, `health`, `pets`, `repairs`, `housing`, `home`, `gifts`, `donations`, `lottery`, `kids`, `utilities`.

**INCOME** (доходи) — 10 категорій:
`salary`, `freelance`, `investment`, `gift`, `bonus`, `rental`, `interest`, `dividend`, `business`, `other`.

**TRANSFER** (переказ) — 2 категорії:
`transfer`, `other`.

При спробі передати категорію, що не входить до відповідного списку для вказаного типу, сервер повертає `422 Unprocessable Entity` з переліком допустимих значень. Повний список категорій для кожного типу доступний через окремий ендпоінт `GET /api/transactions/categories/list` — він не потребує автентифікації і використовується фронтендом для побудови випадаючих меню.

#### CRUD-операції

**Створення** (`POST /api/transactions`). Після валідації та нормалізації полів сервер розраховує вплив транзакції на баланс користувача (`User.capital`) — детально описано нижче — і зберігає запис. Відповідь включає усі поля транзакції та оновлене значення `new_capital`.

**Читання** (`GET /api/transactions/{tx_id}`). Повертає одну транзакцію за її ідентифікатором. Обов'язково перевіряється приналежність: запит на транзакцію іншого користувача повертає `404 Not Found`, а не `403 Forbidden` — щоб не розкривати існування запису.

**Оновлення** (`PATCH /api/transactions/{tx_id}`). Реалізовано як часткове оновлення: оброблюються лише поля, явно передані у тілі запиту (через `model_dump(exclude_unset=True)`). Якщо змінюється тип або категорія — виконується повторна валідація їх сумісності. Теги та категорія повторно нормалізуються до нижнього регістру. Перерахунок `User.capital` при зміні суми або типу **не виконується** — це відома обмеженість поточної реалізації.

**Видалення** (`DELETE /api/transactions/{tx_id}`). Перед видаленням сервер скасовує вплив транзакції на баланс: виконується та сама конвертація суми, але з оберненим знаком, і результат віднімається від `User.capital`. Таким чином баланс завжди відображає лише актуальні записи.

**Список із фільтрацією** (`GET /api/transactions`). Підтримує такі параметри запиту:

| Параметр | Опис |
|---|---|
| `kind` | Фільтр за типом: `EXPENSE`, `INCOME` або `TRANSFER` |
| `category` | Фільтр за назвою категорії (без урахування регістру) |
| `tags` | Рядок із тегами через кому; повертаються транзакції, що містять **усі** перелічені теги одночасно |
| `date_from` / `date_to` | Часовий діапазон (включно) |
| `limit` / `offset` | Пагінація; `limit` від 1 до 1000, за замовчуванням 50 |

Результат впорядковується за датою за спаданням, потім за ідентифікатором за спаданням — щоб транзакції з однаковою датою мали передбачувану послідовність.

#### Оновлення балансу та конвертація валют

Кожна транзакція впливає на поле `User.capital` — агрегований баланс користувача у його валюті за замовчуванням. Оскільки транзакція може бути записана у будь-якій із підтримуваних валют, сума перераховується через проміжну одиницю — **USD**:

```
сума у вихідній валюті
    ÷ rate[вихідна_валюта]     → сума у USD
    × rate[валюта_користувача] → сума у валюті користувача
```

Курси зчитуються з таблиці `currencies`, що оновлюється щогодини від API НБУ. Результат округлюється до двох знаків за правилом `ROUND_HALF_UP`. Для транзакцій типу `EXPENSE` конвертована сума повертається від'ємною — тобто функція `convert_to_user_currency` повертає вже готове значення зміни балансу, яке просто додається до `User.capital`. Для `INCOME` та `TRANSFER` — додатнє.

### 1.4.2 Рекурентні транзакції

Рекурентні транзакції дозволяють автоматизувати регулярні фінансові операції — абонентські платежі, оренду, виплату зарплати тощо. Правило рекурентної транзакції описує шаблон, за яким система самостійно створює реальні транзакції у заданий час. Ендпоінти розміщено за префіксом `/api/transactions/recurring`.

#### Модель та поля

Рекурентні транзакції зберігаються в окремій таблиці `recurring_transactions`. Структура запиту на створення:

| Поле | Тип | Опис |
|---|---|---|
| `name` | `string` | Назва правила (1–64 символи) |
| `amount` | `Numeric(14, 2)` | Сума кожного спрацювання |
| `kind` | `enum` | EXPENSE / INCOME / TRANSFER |
| `category_name` | `string` | Категорія (ті самі правила, що й у звичайних транзакціях) |
| `currency` | `string` | Валюта; якщо не вказана — валюта користувача за замовчуванням |
| `tags` | `string[]` | Теги, що успадковуються кожною породженою транзакцією |
| `note` | `string` | Нотатка (до 512 символів) |
| `frequency` | `enum` | Частота: `DAILY`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`, `YEARLY` |
| `first_run` | `datetime` | Момент першого спрацювання (стає значенням `next_run` у записі) |

Поле `is_active` за замовчуванням дорівнює `true` і дозволяє тимчасово призупинити правило без його видалення.

#### CRUD-операції

Модуль реалізує повний набір операцій:

- `POST /api/transactions/recurring` — створення нового правила;
- `GET /api/transactions/recurring` — список правил з фільтром `is_active` та пагінацією; впорядковано за `next_run` за зростанням;
- `GET /api/transactions/recurring/{rt_id}` — отримання конкретного правила;
- `PATCH /api/transactions/recurring/{rt_id}` — часткове оновлення; дозволяє змінити будь-яке поле, включно з `next_run` та `is_active` для ручного керування розкладом;
- `DELETE /api/transactions/recurring/{rt_id}` — видалення правила (204 No Content).

#### Автоматичне спрацювання — Cron-задача

Основна цінність рекурентних транзакцій полягає у фоновому механізмі їх виконання. При старті застосунку функція `register_recurring_cron()` реєструє задачу `_fire_due_recurring()`, що виконується **щохвилини**.

Логіка кожного запуску:

```
1. Відкрити нову сесію БД (окрему від HTTP-запитів)
2. Вибрати всі записи: is_active = true AND next_run ≤ поточний час
3. Для кожного знайденого правила:
   а. Завантажити відповідного User
   б. Конвертувати суму у валюту користувача
   в. Скоригувати User.capital
   г. Створити новий запис Transaction з параметрами правила
   ґ. Просунути next_run на один кроковий інтервал
4. Зафіксувати зміни (commit) якщо були спрацювання
```

Просування `next_run` реалізовано функцією `_advance_next_run()`. Для частот `DAILY`, `WEEKLY` та `BIWEEKLY` використовується стандартний `timedelta`. Для `MONTHLY` та `YEARLY` — `relativedelta` з бібліотеки `python-dateutil`, що коректно обробляє межі місяців: наприклад, правило із датою 31 січня наступного разу спрацює 28/29 лютого, а не перейде у березень.

| Частота | Інтервал просування |
|---|---|
| `DAILY` | +1 день |
| `WEEKLY` | +7 днів |
| `BIWEEKLY` | +14 днів |
| `MONTHLY` | +1 місяць (через `relativedelta`) |
| `YEARLY` | +1 рік (через `relativedelta`) |

Якщо між двома запусками cron-задачі пройшло більше хвилини (наприклад, сервер перезапускався), при наступному запуску будуть оброблені **всі** правила, у яких `next_run` є у минулому, — жодне спрацювання не буде пропущено. Це є важливою властивістю архітектури: умова `next_run ≤ now` гарантує відновлення після простою.

Обробка помилок у cron-задачі реалізована ізольовано: виняток при обробці одного правила перехоплюється та логується, але не зупиняє обробку решти правил у тому ж циклі. Задача використовує власну сесію БД (`AsyncSessionLocal`), повністю незалежну від HTTP-сесій, що унеможливлює конфлікти транзакцій між фоновим процесом та одночасними запитами користувача.

### 1.4.3 Бюджетування та спільний доступ

Модуль бюджетування дозволяє користувачам організовувати витрати у межах виділених лімітів, а також спільно керувати фінансами разом з іншими учасниками системи. Ендпоінти розміщено за префіксом `/api/budgets`.

#### Структура бюджету

При створенні бюджет описується чотирма полями:

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `name` | `string` | 1–128 символів | Назва бюджету |
| `type` | `enum` | PERSONAL / FAMILY / BUSINESS | Тип бюджету; визначає правила спільного доступу |
| `currency` | `string` | ISO-4217 | Валюта бюджету; за замовчуванням USD |
| `limit_amount` | `Numeric(14, 2)` | > 0; необов'язкове | Граничний ліміт витрат; використовується в аналітиці |

Поле `limit_amount` є необов'язковим і не виконується системою автоматично — воно виступає орієнтиром і передається до аналітичних звітів для порівняння фактичних витрат із плановими. Бюджети типу `PERSONAL` призначені для одного користувача і не можуть мати додаткових учасників; `FAMILY` та `BUSINESS` підтримують спільний доступ.

#### Ролева модель доступу

Доступ до бюджету регулюється через таблицю `budget_members`, що реалізує зв'язок «бюджет — користувач — роль». Система розрізняє три ролі:

| Роль | Права доступу |
|---|---|
| `OWNER` | Повний доступ: читання, редагування, видалення бюджету, управління учасниками |
| `EDITOR` | Читання та редагування полів бюджету (назва, валюта, ліміт) |
| `VIEWER` | Лише читання; не може змінювати бюджет або управляти учасниками |

При **створенні бюджету** власник автоматично додається до таблиці `budget_members` з роллю `OWNER`. Це означає, що список бюджетів користувача формується через JOIN з таблицею учасників — ендпоінт `GET /api/budgets` повертає всі бюджети, у яких поточний користувач є учасником у будь-якій ролі, включно з власними.

#### CRUD-операції над бюджетом

**Створення** (`POST /api/budgets`). Валідує валюту, зберігає бюджет, потім у межах тієї ж транзакції додає запис у `budget_members` з роллю `OWNER`. Обидві операції атомарні.

**Список** (`GET /api/budgets`). Повертає усі бюджети, де поточний користувач є учасником. Запит реалізований через `JOIN` таблиці `Budget` і `BudgetMember` за умовою `BudgetMember.user_id = current_user.id_`. Підтримує пагінацію (`limit`, `offset`).

**Читання** (`GET /api/budgets/{id}`). Перевіряє наявність запису в `budget_members` для поточного користувача. Якщо запису немає — повертає `403 Forbidden`, незалежно від того, чи існує бюджет взагалі.

**Редагування** (`PATCH /api/budgets/{id}`). Доступне лише для ролей `OWNER` та `EDITOR`. Реалізовано як часткове оновлення. Змінити тип бюджету (`type`) через цей ендпоінт неможливо — він відсутній у схемі `BudgetUpdate`.

**Видалення** (`DELETE /api/budgets/{id}`). Доступне виключно власнику (`OWNER`). Видалення бюджету каскадно видаляє всі записи `BudgetMember`, пов'язані з ним.

#### Управління учасниками

Ендпоінти для роботи з учасниками бюджету:

| Метод | URL | Опис |
|---|---|---|
| `GET` | `/api/budgets/{id}/members` | Список учасників; доступний будь-якому учаснику |
| `POST` | `/api/budgets/{id}/members` | Додати учасника; тільки `OWNER` |
| `DELETE` | `/api/budgets/{id}/members/{user_id}` | Видалити учасника; тільки `OWNER` |

Під час додавання учасника система виконує кілька перевірок:

- бюджет не може бути типу `PERSONAL` — особистий бюджет не підтримує учасників (`422`);
- власника бюджету не можна додати повторно як учасника (`422`);
- цільовий користувач повинен існувати в системі (`404`);
- один і той самий користувач не може бути доданий двічі (`409 Conflict`).

Видалення власника з учасників також заблоковано (`422`) — власник завжди залишається у складі бюджету. Видалити власника з бюджету можна лише разом із самим бюджетом.

### 1.4.4 Фінансові цілі

Модуль фінансових цілей реалізує концепцію **накопичувальних «банок»** — ізольованих резервуарів, до яких користувач поступово відкладає кошти для досягнення конкретної мети. Ендпоінти розміщено за префіксом `/api/goals`.

#### Структура цілі

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `name` | `string` | 1–255 символів | Назва цілі |
| `target_amount` | `Numeric(14, 2)` | > 0 | Цільова сума накопичення |
| `saved_amount` | `Numeric(14, 2)` | — | Поточна накопичена сума; встановлюється у 0 при створенні |
| `currency` | `string` | ISO-4217; за замовч. USD | Валюта цілі |
| `description` | `string` | до 512 символів | Необов'язковий опис |
| `deadline` | `datetime` | — | Необов'язковий дедлайн |
| `is_completed` | `bool` | — | Прапорець завершення |
| `completed_at` | `datetime` | — | Момент завершення; `null` якщо активна |

Відповідь сервера (`GoalOut`) містить додаткове обчислювальне поле `progress_percent`, що не зберігається у базі, а обчислюється динамічно під час формування відповіді:

```
progress_percent = min(saved_amount / target_amount × 100, 100.0)
```

Значення округлюється до одного знаку після коми та обмежується максимумом у 100% — навіть якщо внаслідок коригування `target_amount` відсоток перевищить 100. Це поле реалізовано через декоратор `@computed_field` бібліотеки Pydantic v2, що дозволяє включати обчислювані властивості безпосередньо до схеми відповіді без змін у моделі БД.

#### CRUD-операції

**Створення** (`POST /api/goals`). Валідує валюту, встановлює `saved_amount = 0`, зберігає ціль. Поле `is_completed` за замовчуванням `false`.

**Список** (`GET /api/goals`). Підтримує два параметри фільтрації:
- `q` — пошук за назвою з частковим збігом без урахування регістру (через `ILIKE '%q%'`);
- `is_completed` — фільтр за статусом: `true` поверне лише завершені, `false` — лише активні.

Результат впорядковується так, щоб активні цілі завжди відображалися першими: спочатку за `is_completed ASC`, потім за `created_at DESC` всередині кожної групи.

**Редагування** (`PATCH /api/goals/{id}`). Часткове оновлення метаданих: назви, цільової суми, валюти, опису, дедлайну. Схема `GoalUpdate` задекларована з `extra="forbid"`, тому спроба передати невідомі поля повертає `422`.

**Видалення** (`DELETE /api/goals/{id}`). Повністю видаляє ціль разом з усіма її накопиченнями.

#### Операції з накопиченнями

Окрім стандартних CRUD-операцій, модуль реалізує два спеціалізовані ендпоінти для управління сумою накопичень.

**Поповнення** (`POST /api/goals/{id}/deposit`). Додає вказану суму до `saved_amount`. Якщо після поповнення `saved_amount ≥ target_amount`, ціль **автоматично завершується**: `saved_amount` фіксується рівно на рівні `target_amount` (не більше), `is_completed` стає `true`, `completed_at` заповнюється поточним часом. Спроба поповнити вже завершену ціль повертає `409 Conflict`.

**Зняття** (`POST /api/goals/{id}/withdraw`). Зменшує `saved_amount` на вказану суму. Якщо запитувана сума перевищує накопичену, сервер повертає `422` з детальним повідомленням про поточний залишок. Якщо ціль на момент зняття була завершена і після зняття `saved_amount` опускається нижче `target_amount`, ціль **автоматично перевідкривається**: `is_completed` повертається у `false`, `completed_at` — у `null`.

Цей механізм взаємного переходу між станами дозволяє уникнути ситуацій, де ціль залишається «завершеною» з неповною сумою через ручне коригування.

#### Переходи між станами

На додаток до автоматичного завершення при поповненні, модуль надає ендпоінти для ручного управління станом:

**Закрити** (`POST /api/goals/{id}/close`). Позначає ціль як завершену. Якщо `saved_amount < target_amount`, за замовчуванням повертається `422` з повідомленням про недосягнення мети. Для примусового закриття слід передати параметр запиту `?force=true` — це дозволяє закрити ціль достроково, наприклад, якщо мета втратила актуальність.

**Перевідкрити** (`POST /api/goals/{id}/reopen`). Знімає прапорець завершення з уже закритої цілі. Якщо ціль ще не завершена — повертає `409 Conflict`. Після перевідкриття накопичена сума залишається незмінною.

### 1.4.5 Аналітика

Аналітичний модуль надає користувачу узагальнені відомості про його фінансову активність у різних розрізах: загальний огляд балансу, динаміка доходів і витрат у часі, розподіл за категоріями й тегами, а також порівняння фактичних витрат із плановими в межах бюджету. Усі ендпоінти розміщено за префіксом `/api/analytics`.

З архітектурної точки зору модуль побудовано на основі патерну **шаблонного методу**: визначено абстрактний клас `BaseAnalyticsService`, а кожен окремий вид аналітики реалізовано у власному підкласі у директорії `services/`. Базовий клас приймає сесію бази даних, об'єкт поточного користувача, актуальний словник курсів валют та необов'язкову звітну валюту. Він надає двом основним допоміжним методам: `_convert()`, що конвертує суму з довільної валюти у звітну через USD як проміжну, та `_signed()`, що повертає суму зі знаком відповідно до типу транзакції — позитивним для доходів і від'ємним для витрат. Конкретний аналітичний клас зобов'язаний реалізувати лише один асинхронний метод `compute()` з необхідними параметрами.

Важливою особливістю є те, що курси валют завантажуються з бази даних лише **один раз на запит** через спільну FastAPI-залежність `_ctx`. Ця залежність одночасно забезпечує доступ до сесії, об'єкта користувача, словника курсів і звітної валюти для будь-якого ендпоінту модуля. Всі ендпоінти підтримують необов'язковий параметр `?currency=EUR`, що дозволяє отримати результат у будь-якій підтримуваній валюті незалежно від налаштованої валюти за замовчуванням.

Модуль реалізує сім аналітичних звітів.

**Загальний огляд** (`GET /api/analytics/overview`) повертає ключові показники за вказаний часовий діапазон: загальну суму доходів, загальну суму витрат, їх різницю (net) та поточний баланс `User.capital`. Діапазон задається параметрами `date_from` та `date_to`; якщо вони відсутні — аналізуються всі транзакції.

**Місячні тренди** (`GET /api/analytics/trends/monthly`) повертають порівняння доходів і витрат по місяцях за вказану кількість останніх місяців (параметр `months`, від 1 до 60, за замовчуванням 12). Результат завжди містить рівно стільки точок, скільки запитано — місяці без жодної транзакції заповнюються нульовими значеннями. Це архітектурне рішення забезпечує передачу клієнтській частині рівномірної часової серії даних без пропусків, придатної для безпосередньої побудови графіка. **Річні тренди** (`GET /api/analytics/trends/yearly`) реалізовані аналогічно, але узагальнюють дані по роках.

**Порівняння періодів** (`GET /api/analytics/comparison/period`) порівнює доходи та витрати поточного вікна з попереднім еквівалентним. Підтримуються три режими: `monthly` зіставляє поточний календарний місяць із попереднім, `yearly` — поточний рік із минулим, а `custom` приймає довільний діапазон `date_from`/`date_to` і автоматично обчислює попереднє вікно тієї ж тривалості. Результат містить абсолютну різницю та відсоткову зміну для доходів і витрат; якщо попереднє значення дорівнює нулю, відсоткова зміна повертається як `null` з метою уникнення ділення на нуль.

**Розбивка за категоріями** (`GET /api/analytics/breakdown/categories`) підраховує суму транзакцій у кожній категорії за вказаний діапазон. Фільтр `kind` дозволяє отримати окремо статистику витрат або доходів. Результат призначений для побудови кругових або стовпчастих діаграм. Аналогічним чином працює **розбивка за тегами** (`GET /api/analytics/breakdown/tags`), яка виконує агрегацію по полю `tags`.

**Порівняння з бюджетом** (`GET /api/analytics/budgets/{budget_id}`) зіставляє фактичні витрати у межах конкретного бюджету з його лімітом `limit_amount` за вказаний період. Якщо ліміт не встановлено, відповідне поле у відповіді дорівнює `null`.

### 1.4.6 Конвертація валют та інтеграція з API НБУ

Підтримка мультивалютності є наскрізною функціональністю платформи: транзакції можуть записуватися у будь-якій підтримуваній валюті, а баланс і аналітичні звіти завжди відображаються у валюті, зручній для конкретного користувача. Основою цього механізму є таблиця `currencies`, що зберігає актуальні курси відносно долара США, та зовнішня інтеграція з API Національного банку України.

Модуль курсів валют розміщено за префіксом `/api/currencies` і надає доступ до збережених курсів у режимі лише для читання. Щогодини cron-задача `register_currency_cron()`, що реєструється під час запуску застосунку, виконує запит до NBU API за адресою, заданою змінною оточення `NBU_API_URL`. API повертає масив об'єктів, де кожен елемент містить код валюти (`cc`) та її курс у гривнях (`rate`). Оскільки все подальше обчислення в системі використовує долар як проміжну одиницю, отримані курси одразу перераховуються у USD-відносний формат. Логіка перерахунку наступна: із відповіді витягується курс долара до гривні (`usd_uah`), після чого для кожної іншої валюти обчислюється відношення `usd_uah / rate_uah`. Таким чином, у таблиці зберігається значення «скільки одиниць цієї валюти дорівнює одному долару» — тобто USD = 1.0, UAH ≈ 37.25, EUR ≈ 0.92 і так далі.

Збереження курсів реалізовано через PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` (upsert), що дозволяє оновити наявні записи або додати нові за один SQL-запит без попередньої перевірки існування. Якщо запит до NBU API завершується помилкою (таймаут або HTTP-помилка), виняток логується, але не зупиняє роботу застосунку — система продовжує використовувати курси з попереднього успішного оновлення.

Безпосередню конвертацію суми виконує функція `convert_to_user_currency()` у модулі `transactions/currency_converter.py`. Вона отримує словник курсів із бази, після чого застосовує двокрокову формулу: спочатку сума ділиться на курс вихідної валюти відносно долара, що дає проміжну суму в USD, а потім множиться на курс цільової валюти, отримуючи підсумкове значення. Якщо вихідна і цільова валюти збігаються, конвертація пропускається. Результат округлюється до двох знаків після коми за правилом `ROUND_HALF_UP`. Для транзакцій типу `EXPENSE` функція повертає від'ємне значення, що безпосередньо додається до поля `User.capital`, — завдяки цьому логіка оновлення балансу залишається єдиним рядком коду у будь-якому місці системи.

Цей самий механізм конвертації використовується і в аналітичних сервісах — через метод `_convert()` базового класу `BaseAnalyticsService`, — що гарантує узгодженість результатів незалежно від того, у якій валюті зберігається кожна окрема транзакція.

### 1.4.7 Завантаження файлів та OCR-розпізнавання чеків

Модуль роботи з файлами дозволяє користувачу прикріплювати скани або фотографії касових чеків до своїх фінансових записів. При завантаженні система автоматично намагається розпізнати текст на чеку і витягнути з нього корисні дані: суму, назву магазину та категорію витрат. Ендпоінти розміщено за префіксом `/api/files`.

Перед збереженням файлу сервер виконує дві перевірки. По-перше, перевіряється MIME-тип: підтримуються зображення у форматах JPEG, PNG, WEBP, GIF та документи PDF — будь-який інший тип повертає `415 Unsupported Media Type`. По-друге, перевіряється розмір: весь вміст файлу зчитується у пам'ять і порівнюється з лімітом, що задається змінною оточення `MAX_UPLOAD_SIZE_MB` (за замовчуванням 20 МБ); файли більшого розміру відхиляються зі статусом `413`.

Файли зберігаються локально у директорії, заданій змінною `UPLOAD_DIR`, за шляхом `<user_id>/<uuid><розширення>`. Використання UUID як імені файлу усуває можливість атак через підбір або перезапис шляху. Запис і читання файлів виконуються через бібліотеку `aiofiles`, що забезпечує асинхронну роботу з файловою системою без блокування циклу подій. Логіка зберігання інкапсульована у клас `LocalStorageService`, що успадковує абстрактний `BaseStorageService` — у разі потреби переходу на хмарне сховище достатньо реалізувати новий підклас і замінити один рядок у роутері.

OCR-аналіз запускається одразу після збереження файлу. Оскільки розпізнавання тексту є обчислювально затратною синхронною операцією, її виконання делегується до системного пулу потоків через `asyncio.to_thread()` — це запобігає блокуванню асинхронного циклу подій під час обробки.

Сам OCR-сервіс (`ocr_service.py`) підтримує два типи вхідних даних. Для PDF-файлів текст витягується бібліотекою `pdfplumber`, яка не потребує жодних зовнішніх системних залежностей і працює безпосередньо з байтовим потоком. Для зображень використовується конвеєр на основі OpenCV (`image_preprocess.py`). Спершу на фото шукаються QR-коди: кожен український фіскальний чек містить QR-код з посиланням на кабінет платника ДПС (`cabinet.tax.gov.ua/cashregs/check?date=…&time=…&sm=<сума>&fn=…`), з якого сума і час покупки беруться точно, незалежно від якості розпізнавання тексту. Далі на фото знаходиться сам чек: будується кілька масок «паперу» (відстань кольору від фону, визначеного за краями кадру; низька насиченість; низька хроматичність; яскравість) і обирається перша, найбільша область якої добре описується чотирикутником. Ця область вирівнюється перспективним перетворенням, що прибирає стіл і виправляє нахил камери. Вирізаний чек збільшується до ширини ~1400 px, освітлення вирівнюється діленням на оцінений фон паперу (тіні зникають), після чого зображення бінаризується методом Оцу. Розпізнавання виконується кількома проходами Tesseract (`ukr`, `eng`, `ukr` з `--psm 4`) до першого результату з достатньою впевненістю; окремі мови дають кращий результат, ніж комбінація `ukr+eng`, яка плутає кирилицю з подібною латиницею. Рядки із середньою впевненістю Tesseract нижче 55 % відкидаються як шум (псевдографіка номера замовлення, QR-коди, текстура столу). Без OpenCV використовується простіший шлях через `Pillow` (поворот за EXIF, відтінки сірого, збільшення, автоконтраст). Мови можна задати змінною `OCR_LANG` (через кому), а шлях до виконуваного файлу Tesseract — змінною `TESSERACT_CMD`. Важливою особливістю є **м'яке підключення** обох бібліотек: якщо `pytesseract` або `pdfplumber` не встановлені, або якщо двійковий файл Tesseract відсутній у системі, модуль перехоплює відповідний виняток і продовжує функціонування у режимі деградованої доступності — файл зберігається, але результат OCR повертає порожні поля і `confidence = "none"`.

Інтерпретацію сирого тексту винесено в окремий модуль `receipt_parser.py`, що складається лише з чистих функцій і тому легко покривається модульними тестами. Грошові суми розпізнаються у форматах `25.50`, `1234,50`, `1,234.50`, `1.234,50` та `2 402,13`; дати на кшталт `12.03.2026` не сприймаються як суми. Підсумок чека шукається за мітками у порядку пріоритету: спершу «До сплати», «Amount due», «Grand total», потім «Сума», «Разом», «Total»; рядки з «Subtotal», «ПДВ», «Знижка», «Готівка», «Решта» ігноруються. Якщо мітки немає, береться найбільша сума (без урахування внесеної готівки та решти) зі зниженою впевненістю. Валюта визначається за символами та словами (`₴`, `грн`, `$`, `EUR` тощо), дата — за форматами `дд.мм.рррр` та ISO з перевіркою, що вона не в майбутньому і не старша за два роки (для чеків у доларах неоднозначні дати читаються у форматі «місяць/день»). Назва магазину береться з перших рядків чека з пропуском адрес, податкових номерів і службових рядків та з видаленням організаційно-правової форми (ТОВ, ФОП, LLC). Категорія визначається за словником відомих брендів (АТБ, Сільпо, WOG, OKKO, Rozetka тощо, вага 3) та загальних ключових слів (вага 1) з урахуванням меж слів, причому збіги у назві магазину мають подвійну вагу; усі категорії належать до дозволеного переліку витрат. Кожне поле має власну оцінку впевненості від 0 до 1, а загальна оцінка `confidence_score` є їх зваженою сумою (сума — 0,5, категорія — 0,2, дата і магазин — по 0,15), яка також виражається міткою `confidence`: `"high"`, `"medium"`, `"low"` або `"none"`.

На основі розпізнаних даних сервер формує **чернетку транзакції** (`TransactionDraft`), яку повертає одразу у відповіді на завантаження. Користувач може підтвердити її одним натисканням — запитом `POST /api/files/receipts/{id}/transaction` з порожнім тілом — або змінити окремі поля і надіслати лише їх: вони мають пріоритет над розпізнаними значеннями. Транзакція створюється тим самим сервісом `create_user_transaction`, що й при ручному введенні (з перевіркою категорії, конвертацією валюти та оновленням капіталу), і в межах однієї транзакції БД прив'язується до чека. Повторне підтвердження вже прив'язаного чека повертає `409`, а відсутність суми — `422`. Параметр `?auto_create=true` при завантаженні дозволяє створити транзакцію одразу, якщо підсумок знайдено (за замовчуванням вимкнено). Ендпоінт `GET /api/files/receipts/{id}/draft` повторно розбирає збережений текст актуальною версією парсера, а `POST /api/files/receipts/{id}/rescan` заново запускає OCR для збереженого файлу.

Весь результат OCR зберігається у таблиці `receipts` у колонці типу `JSON`, що дозволяє фронтенду відображати як сирий розпізнаний текст, так і структуровані поля без додаткових запитів. Чек може бути пов'язаний з конкретною транзакцією через ендпоінт `PATCH /api/files/receipts/{id}/link` — або відв'язаний, якщо передати `transaction_id = null`. Завантаження оригінального файлу на диск доступне через `GET /api/files/receipts/{id}/download`, що повертає відповідь типу `FileResponse` з відповідним `Content-Type` і оригінальним ім'ям файлу.

### 1.4.8 Імпорт транзакцій з CSV / Excel

Модуль масового імпорту дозволяє користувачу завантажити файл у форматі CSV або Excel і автоматично створити одразу кілька транзакцій за одним запитом. Це зручно для перенесення даних з інших фінансових застосунків або банківських виписок. Ендпоінт розміщено за адресою `POST /api/transactions/import` і потребує автентифікації.

#### Підтримувані формати та структура файлу

Сервер приймає файли з розширеннями `.csv`, `.xlsx` та `.xls`. Перший рядок кожного файлу повинен бути рядком заголовків. Нижче наведено список стовпців:

| Стовпець | Обов'язковий | Опис |
|---|---|---|
| `name` | ✓ | Назва транзакції; обрізається до 64 символів |
| `amount` | ✓ | Сума; повинна бути додатнім десятковим числом |
| `kind` | ✓ | Тип: `EXPENSE`, `INCOME`, `TRANSFER` або числові еквіваленти `0`, `1`, `2` |
| `category_name` | ✓ | Категорія; перевіряється проти дозволених списків |
| `currency` | — | ISO-код валюти; якщо відсутній — використовується валюта за замовчуванням користувача |
| `date` | — | Дата транзакції у будь-якому форматі, що розпізнається `dateutil.parser`; якщо відсутня — проставляється поточний час |
| `tags` | — | Теги, розділені `\|` або `,`; нормалізуються до нижнього регістру |
| `note` | — | Довільна нотатка; обрізається до 512 символів |

Назви стовпців нечутливі до регістру та пробілів — `Name`, `AMOUNT`, ` Kind ` усі є рівнозначними. CSV-файли зчитуються з підтримкою BOM-заголовку (`utf-8-sig`), що забезпечує сумісність із файлами, збереженими Microsoft Excel.

Підтримка Excel реалізована через бібліотеку `openpyxl`, яка є **м'якою залежністю**: якщо бібліотека не встановлена, спроба завантажити `.xlsx`-файл повертає `501 Not Implemented` без аварійного завершення роботи застосунку.

#### Потік обробки та валідація

Після зчитування файлу сервер виконує посторядову валідацію через функцію `_parse_rows()`. Для кожного рядка перевіряється наявність обов'язкових стовпців, правильність формату суми, коректність типу транзакції та допустимість категорії для вказаного типу (ті самі правила, що і при ручному створенні). Валідація є **м'якою**: некоректні рядки не призупиняють весь імпорт, а додаються до списку помилок; усі коректні рядки обробляються далі.

Для кожного валідного рядка виконується та сама послідовність, що і при ручному створенні транзакції: конвертація суми у валюту користувача, оновлення `User.capital` та збереження запису `Transaction`. Якщо конвертація для конкретного рядка завершилася помилкою (наприклад, невідомий код валюти), рядок пропускається з відповідним повідомленням у списку помилок, але решта рядків продовжують оброблятися.

Усі коректні транзакції зберігаються **за один `commit`**, після чого виконується оновлення об'єкту `User`.

#### Відповідь

Ендпоінт завжди повертає структуровану відповідь, незалежно від кількості помилок:

```json
{
  "imported": 42,
  "skipped": 3,
  "errors": [
    "Row 5: invalid amount '–'",
    "Row 11: Unknown income category 'misc'..."
  ],
  "new_capital": 15420.50
}
```

| Поле | Опис |
|---|---|
| `imported` | Кількість успішно створених транзакцій |
| `skipped` | Кількість пропущених рядків |
| `errors` | Список текстових описів помилок із номером рядка |
| `new_capital` | Оновлений баланс користувача після імпорту |

Якщо файл порожній або містить лише заголовок без жодного рядка даних, повертається `422 Unprocessable Entity` ще до початку обробки.

### 1.4.9 Налаштування профілю та підписки

Модуль налаштувань надає користувачу централізований інтерфейс для керування особистими даними, валютними вподобаннями, адресою електронної пошти, параметрами сповіщень та рівнем підписки. Усі ендпоінти розміщено за префіксом `/api/settings` і потребують автентифікації.

#### Профіль (`/api/settings/profile`)

Ендпоінт `GET /api/settings/profile` повертає повну інформацію профілю поточного користувача. Відповідь схеми `ProfileOut` містить такі поля:

| Поле | Опис |
|---|---|
| `id_` | Числовий ідентифікатор |
| `username` | Ім'я користувача |
| `email` | Електронна пошта |
| `avatar_url` | URL зображення аватара (до 512 символів); `null` якщо не встановлено |
| `timezone` | Часовий пояс у форматі IANA (до 64 символів); `null` якщо не встановлено |
| `default_currency` | Валюта за замовчуванням (ISO-4217) |
| `twofa_enabled` | Стан двофакторної автентифікації |
| `subscription_plan` | Поточний план: `FREE` або `PRO` |

Ендпоінт `PATCH /api/settings/profile` дозволяє оновити `username`, `avatar_url` та `timezone` — будь-яку підмножину цих полів одночасно (часткове оновлення). Схема `ProfileUpdate` оголошена з `extra="forbid"`, тому передача будь-якого невідомого поля повертає `422`. При зміні `username` сервер перевіряє унікальність нового значення серед усіх користувачів — конфлікт повертає `409 Conflict`.

#### Валюта за замовчуванням (`/api/settings/currency`)

`GET /api/settings/currency` повертає поточну валюту за замовчуванням. `PATCH /api/settings/currency` дозволяє змінити її, передавши тіло `{"default_currency": "EUR"}`. Значення перевіряється проти переліку `Currencies` enum — спроба встановити непідтримуваний код повертає `422`. Зміна валюти за замовчуванням не перераховує наявні транзакції та баланс — вона впливає лише на нові транзакції та аналітику.

#### Електронна пошта (`/api/settings/email`)

`PATCH /api/settings/email` змінює адресу електронної пошти. Сервер перевіряє, що нова адреса відрізняється від поточної (`409` при збігу) та не зайнята іншим акаунтом (`409` при конфлікті). Нова адреса автоматично приводиться до нижнього регістру перед збереженням. Верифікаційний лист на нову адресу в поточній реалізації не надсилається — це позначено у коді як `TODO` для майбутньої інтеграції.

#### Налаштування сповіщень (`/api/settings/notifications`)

Модуль реалізує детальний контроль над каналами та подіями сповіщень. Запис у таблиці `notification_preferences` **не створюється при реєстрації** — замість цього він ліниво ініціалізується з налаштуваннями за замовчуванням при першому виклику `GET /api/settings/notifications`. Функція `_get_or_create_prefs()` реалізує цю логіку і є єдиним коректним способом отримати або створити запис — звертатися до таблиці безпосередньо не слід.

Налаштування розподілені на два рівні: **канали** визначають, якими шляхами надсилаються повідомлення, а **події** — за яких обставин вони відправляються.

| Поле | Тип | За замовч. | Опис |
|---|---|---|---|
| `email_enabled` | `bool` | `true` | Канал: сповіщення на email |
| `push_enabled` | `bool` | `false` | Канал: push-сповіщення |
| `budget_limit_alerts` | `bool` | `true` | Подія: наближення до ліміту бюджету |
| `recurring_reminders` | `bool` | `true` | Подія: нагадування перед спрацюванням рекурентної транзакції |
| `goal_milestone_alerts` | `bool` | `true` | Подія: досягнення проміжної позначки цілі (25 / 50 / 75 / 100 %) |
| `monthly_summary` | `bool` | `true` | Подія: місячний підсумковий дайджест |

`PATCH /api/settings/notifications` підтримує часткове оновлення — можна змінити лише одне конкретне поле, не зачіпаючи решту. Схема `NotificationPreferencesUpdate` також має `extra="forbid"`, що захищає від передачі некоректних назв полів.

#### Управління підпискою (`/api/settings/subscription`)

Система розрізняє два рівні підписки: `FREE` та `PRO`. `GET /api/settings/subscription` повертає поточний план і сформований список функцій із прапорцем доступності для кожної. Список обчислюється динамічно функцією `_build_features()` при кожному запиті.

Функції, доступні виключно на плані `PRO`:

- Необмежена кількість транзакцій, цілей та бюджетів
- Розширена аналітика
- Рекурентні транзакції
- Масовий імпорт CSV / Excel
- Управління учасниками бюджету
- Пріоритетна підтримка

Функції, доступні на обох планах:

- Базова панель керування
- До 3 фінансових цілей
- До 50 транзакцій на місяць
- 1 персональний бюджет

**Підвищення плану** (`POST /api/settings/subscription/upgrade`) встановлює `subscription_plan = PRO`. Якщо план вже `PRO` — повертається `409 Conflict`. **Зниження плану** (`POST /api/settings/subscription/downgrade`) встановлює `subscription_plan = FREE` аналогічно. Обидва ендпоінти оновлюють поле безпосередньо без перевірки оплати — інтеграція з платіжним провайдером позначена у коді як `TODO` і має бути реалізована на рівні роутера.

### 1.4.10 Інтерактивна аналітика та обробка даних

Аналітика є центральним компонентом платформи, що перетворює сирі фінансові записи на структуровану картину фінансової поведінки користувача. Вся обробка виконується на серверній стороні: клієнт отримує вже агреговані числові значення, готові до безпосередньої побудови інтерактивних графіків і таблиць.

Ключовою архітектурною особливістю модуля є єдина точка входу для даних — спільна залежність `_ctx`, що ін'єктується у кожен аналітичний ендпоінт. Вона виконує рівно один запит до таблиці `currencies` за час обробки HTTP-запиту, отримуючи актуальний словник курсів, і передає його разом із сесією та об'єктом користувача в аналітичний сервіс. Завдяки цьому незалежно від того, скільки різних валют зустрічається у транзакціях, накладні витрати на читання курсів фіксовані.

Усі аналітичні сервіси наслідують абстрактний клас `BaseAnalyticsService`. Він реалізує два спільних для всіх звітів операції: конвертацію суми з довільної валюти у звітну через USD як проміжну одиницю, та присвоєння знаку — доходи залишаються позитивними, витрати стають від'ємними. Кожен конкретний клас реалізує лише один асинхронний метод `compute()`, що виконує специфічну агрегацію по базі даних.

Модуль реалізує **сім аналітичних звітів**:

1. **Загальний огляд** — сумарні доходи, витрати та чистий баланс за довільний часовий діапазон.
2. **Місячні тренди** — динаміка доходів і витрат помісячно; повертає рівномірну часову серію без пропусків навіть для місяців без транзакцій.
3. **Річні тренди** — аналогічна агрегація, але по роках.
4. **Порівняння з попереднім періодом** — зіставлення поточного часового вікна з попереднім еквівалентним; підтримує режими `monthly`, `yearly` та `custom` з автоматичним обчисленням попереднього вікна.
5. **Розбивка за категоріями** — розподіл сум по категоріях транзакцій; призначений для кругових і стовпчастих діаграм.
6. **Розбивка за тегами** — аналогічна агрегація по довільних мітках транзакцій.
7. **Виконання бюджету** — фактичні витрати в межах конкретного бюджету зіставляються з його лімітом за вказаний період.

Усі звіти підтримують необов'язковий параметр `?currency=CODE`, що дозволяє отримати результат у будь-якій валюті незалежно від персональних налаштувань. Якщо валюта не вказана, використовується `default_currency` поточного користувача.

Клієнтська частина (React) приймає ці дані і відображає їх через бібліотеки інтерактивної візуалізації: лінійні та стовпчасті графіки для трендів, кругові діаграми для розбивки, прогрес-індикатори для виконання бюджетів і цілей. Такий поділ відповідальностей — сервер агрегує, клієнт відображає — спрощує тестування та незалежну заміну шару візуалізації.

## 1.5 Міграції бази даних та засоби розробки

### Налаштування середовища

Усі змінні оточення зчитуються з файлу `src/.env`, який завантажується при старті через `load_dotenv()` з явно вказаним шляхом у `src/config.py`. Файл `.env` не включається у систему контролю версій і має бути створений вручну перед першим запуском. Обов'язкові змінні поділяються на кілька груп.

Для підключення до бази даних потрібні `POSTGRES_USER`, `POSTGRES_PASSWORD`, `DB_HOST`, `DB_PORT` та `DB_NAME` — з них `config.py` збирає рядок підключення у форматі `postgresql+asyncpg://...`. Для роботи JWT необхідні `SECRET_KEY` (довільний рядок для підпису токенів), `ALGORITHM` (зазвичай `HS256`), `ACCESS_TOKEN_EXPIRE_MINUTES` та `REFRESH_TOKEN_EXPIRE_DAYS`. Для отримання курсів валют потрібен `NBU_API_URL`. Для соціальної автентифікації — чотири змінні: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GITHUB_CLIENT_ID` та `GITHUB_CLIENT_SECRET`. Змінні `UPLOAD_DIR` та `MAX_UPLOAD_SIZE_MB` мають значення за замовчуванням (`./uploads` та `20` відповідно) і можуть бути опущені.

Окремо варто звернути увагу на дублювання конфігурації: файл `src/utils/config.py` також зчитує `ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES` та `REFRESH_TOKEN_EXPIRE_DAYS`, але через bare `load_dotenv()` без явного шляху. Це означає, що ці три змінні повинні бути присутні у змінних середовища оболонки або у `.env`-файлі у поточній робочій директорії — інакше `jwt_handlers.py`, який імпортує їх саме з `utils/config.py`, отримає значення за замовчуванням замість реальних.

### Запуск застосунку

Застосунок запускається виключно командою `python -m src.app` з кореневої директорії репозиторію. Варіант `python src/app.py` є некоректним, оскільки в цьому разі Python не додає кореневу директорію до `sys.path`, і відносні імпорти на кшталт `from src.config import ...` завершуються помилкою. Команда `python -m src.app` автоматично реєструє корінь як пакет та коректно вирішує всі імпорти.

Після успішного старту Uvicorn починає слухати на `127.0.0.1:8000`. Перевірити доступність сервісу можна запитом `GET /health/` — у відповідь повертається `{"status": "OK"}`. Цей ендпоінт не потребує автентифікації і призначений для автоматизованих перевірок живості (health checks) у середовищах розгортання.

### Міграції Alembic

Конфігурація Alembic знаходиться у файлі `alembic.ini` у корені репозиторію. Файл `alembic/env.py` підключає асинхронний рушій SQLAlchemy безпосередньо з `src/config.py::DATABASE_URL` і передає `Base.metadata` — зведений реєстр усіх ORM-моделей із `src/models.py` — як `target_metadata`. Завдяки цьому автогенерація ревізій (через `alembic revision --autogenerate`) порівнює поточний стан класів у `models.py` зі схемою у базі та генерує необхідні SQL-операції.

Оскільки SQLAlchemy працює у асинхронному режимі, `env.py` запускає міграції через `asyncio.run()`: усередині він відкриває `AsyncEngine`, але передає синхронне підключення у `connection.run_sync()`, щоб Alembic, який є синхронним інструментом, міг виконувати SQL-команди у звичному режимі.

Поточний ланцюжок ревізій нараховує шість кроків. Перша ревізія `b8e9f36a3ab8` була початковою і в одній міграції створила всі базові таблиці: `users`, `currencies`, `transactions`, `goals`, `notifications`, `budgets` та `budget_members`. Друга ревізія `e5a8c12f4b76` додала до транзакцій поля `tags` (масив рядків) та `note`, а також створила нову таблицю `recurring_transactions` з усіма необхідними колонками та перечисленнями. Третя ревізія `f1a2b3c4d5e6` доповнила таблицю `budgets` необов'язковою колонкою `limit_amount`. Четверта ревізія `a1b2c3d4e5f6` суттєво переробила таблицю `goals` — перейменувала `summ` і `saved` у `target_amount` та `saved_amount`, змінила їх тип з `Float` на `Numeric(14, 2)` для усунення похибок із плаваючою комою, і додала нові поля: `currency`, `description`, `deadline`, `is_completed`, `completed_at` та `created_at`. П'ята ревізія `b2c3d4e5f6a7` додала до таблиці `users` колонки `avatar_url` та `subscription_plan`, а також створила нову таблицю `notification_preferences` для зберігання налаштувань сповіщень. Шоста і остання ревізія `c3d4e5f6a7b8` створила таблицю `receipts` для зберігання метаданих завантажених файлів-чеків із зовнішніми ключами до `users` та `transactions`.

Для застосування всіх ревізій до порожньої бази достатньо однієї команди `alembic upgrade head` — Alembic самостійно визначає поточну версію схеми і виконує лише ті кроки, яких ще не було застосовано.

Якщо у моделях `src/models.py` вносяться структурні зміни, обов'язково потрібно створювати нову ревізію командою `alembic revision --autogenerate -m "<опис>"` і перевіряти згенерований файл перед застосуванням — автогенерація не завжди коректно обробляє перейменування колонок та зміни типів перечислень.

### Засів тестових даних

Для прискорення локальної розробки передбачено ендпоінт `POST /api/dev/seed`, що не потребує автентифікації. Він створює 10 тестових користувачів з унікальними ім'ями та email-адресами на домені `example.com`, а для кожного з них — 20 транзакцій з випадковими сумами (від 1 до 1000), типами, категоріями, валютами та датами у межах останніх 120 днів. Пароль усіх тестових користувачів — `password123`. Ендпоінт зареєстрований у модулі `src/for_testing/dev_router.py` і призначений виключно для локального середовища — у виробничому розгортанні він повинен бути відключений або прихований за мережевими правилами доступу.

### Логування

Застосунок веде два потоки логів одночасно. Перший — текстовий файл `logs.log` у кореневій директорії репозиторію, що зберігає записи рівня `INFO` та вище у форматі `timestamp - рівень - повідомлення`. Другий — вивід у консоль рівня `DEBUG`, що зручно під час розробки. Логування налаштовується у `src/config.py` через стандартний модуль `logging`. Ключові події — реєстрація та вхід користувачів, завантаження файлів, підсумки cron-задач — логуються явно у відповідних обробниках через `logger.info()`.

## 1.6 Проектування та структура бази даних

Для зберігання даних обрано реляційну систему управління базами даних **PostgreSQL**. Вибір зумовлений широкими можливостями СУБД: підтримкою складних типів даних (зокрема, нативного типу `ARRAY(String)` для тегів транзакцій), розвиненою системою обмежень цілісності (`CHECK`, `UNIQUE`, `FOREIGN KEY`), надійною транзакційністю за стандартом ACID та масштабованістю, достатньою для фінансового застосунку з кількома тисячами активних користувачів.

Схема бази даних спроектована відповідно до принципів нормалізації (третя нормальна форма) та охоплює десять взаємопов'язаних таблиць. Кожна сутність відображається на відповідний ORM-клас у файлі `src/models.py`. Усі первинні ключі іменуються `id_` (не `id`) — це проектне рішення дозволяє уникнути конфлікту із вбудованою функцією Python `id()`.

**Таблиця: `users`** — центральна сутність системи, до якої прямо або опосередковано прив'язані всі інші таблиці.

| Поле | Тип | Обмеження | Опис |

| `email` | `VARCHAR(255)` | `NOT NULL`, `UNIQUE` | Електронна адреса |

| `name` | `VARCHAR(255)` | `NOT NULL` | Назва фінансової цілі |
| `target_amount` | `NUMERIC(14, 2)` | `NOT NULL` | Цільова сума для накопичення |
| `saved_amount` | `NUMERIC(14, 2)` | `NOT NULL`, `DEFAULT 0` | Поточна накопичена сума |
| `currency` | `VARCHAR(3)` | `NOT NULL`, `DEFAULT 'USD'` | Валюта цілі |
| `description` | `VARCHAR(512)` | `NULL` | Довільний текстовий опис |
| `deadline` | `TIMESTAMPTZ` | `NULL` | Бажана дата досягнення цілі |
| `is_completed` | `BOOLEAN` | `NOT NULL`, `DEFAULT FALSE` | Прапорець виконання цілі |
| `completed_at` | `TIMESTAMPTZ` | `NULL` | Дата та час фактичного досягнення |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()` | Дата створення |

**Особливості:** при поповненні цілі через `PATCH /api/goals/{id_}/deposit` система порівнює `saved_amount` з `target_amount` і ��втоматично встановлює `is_completed = TRUE` та заповнює `completed_at` у момент досягнення або перевищення цільової суми. Тип `NUMERIC(14, 2)` гарантує точність фінансових обчислень без похибок плаваючої коми.

### 1.6.9 Чеки та OCR-результати

**Таблиця: `receipts`** — зберігає метадані завантажених файлів-чеків (зображень або PDF) та результати їх автоматичного розпізнавання.

| Поле | Тип | Обмеження | Опис |
|---|---|---|---|
| `id_` | `INTEGER` | `PRIMARY KEY`, `AUTOINCREMENT` | Унікальний ідентифікатор чека |
| `user_id` | `INTEGER` | `NOT NULL`, `INDEX`, `FK → users.id_ CASCADE` | Власник файлу |
| `transaction_id` | `INTEGER` | `NULL`, `INDEX`, `FK → transactions.id_ SET NULL` | Прив'язана транзакція (необов'язково) |
| `original_filename` | `VARCHAR(255)` | `NOT NULL` | Оригінальна назва файлу, завантаженого користувачем |
| `stored_filename` | `VARCHAR(255)` | `NOT NULL` | UUID-базована назва файлу на диску (без пройому шляху) |
| `file_path` | `VARCHAR(512)` | `NOT NULL` | Відносний шлях до файлу всередині `UPLOAD_DIR` |
| `content_type` | `VARCHAR(64)` | `NOT NULL` | MIME-тип файлу (`image/jpeg`, `application/pdf` тощо) |
| `file_size` | `INTEGER` | `NOT NULL` | Розмір файлу у байтах |
| `ocr_result` | `JSON` | `NULL` | JSON-об'єкт із результатами OCR-розпізнавання |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL`, `DEFAULT NOW()` | Дата та час завантаження |

**Особливості:** зовнішній ключ `transaction_id` використовує стратегію `ON DELETE SET NULL` — при видаленні транзакції чек зберігається, але втрачає прив'язку. Фізичний файл зберігається у директорії `UPLOAD_DIR/<user_id>/<uuid><ext>`. Поле `ocr_result` містить структурований JSON з полями `raw_text`, `confidence` та розпізнаними числовими значеннями; якщо OCR недоступний (відсутній Tesseract), поле залишається `NULL`.

### 1.6.10 Зв'язки між сутнос��ями та цілісність даних

Реляційна модель бази даних організована навколо центральної сутності `users`. Кожен користувач може мати довільну кількість транзакцій, рекурентних правил, фінансових цілей, бюджетів (де він є власником), членств у чужих бюджетах, сповіщень та завантажених чеків. Усі ці зв'язки реалізовані як "один до багатьох" (1:N) із каскадним видаленням (`ON DELETE CASCADE`), що гарантує відсутність "осиротілих" записів після видалення облікового запису.

Єдиним винятком є зв'язок `receipts → transactions`: він використовує стратегію `ON DELETE SET NULL`, що дозволяє зберегти файли чеків навіть після видалення відповідної транзакції.

Зв'язок між `budgets` та `users` є відношенням "багато до багатьох" (N:M), реалізованим через проміжну таблицю `budget_members`. Унікальне обмеження `uq_budget_member_budget_user` на пару (`budget_id`, `user_id`) запобігає дублюванню членства.

Для забезпечення доменної цілісності в системі застосовуються:
- **`ENUM`-типи** для полів з фіксованим набором значень: `UserStatus`, `TransactionKind`, `BudgetType`, `BudgetRole`, `RecurringFrequency`, `SubscriptionPlan`;
- **`CHECK`-обмеження** для валідації кодів валют у таблицях `users` та `budgets`;
- **`UNIQUE`-обмеження** для полів `username` та `email` у `users`, а також для зв'язку `user_id` у `notification_preferences`;
- **`NOT NULL`**-обмеження на всі бізнес-критичні поля з явно визначеними значеннями за замовчуванням.

Таким чином, спроектована база даних забезпечує ефективне управління фінансовою інформацією користувачів, підтримує масштабованість та розширюваність системи. Чітка модульна структура сутностей і розвинена система обмежень цілісності дозволяють легко додавати нові функціональні можливості — такі як аналітика витрат, інтеграція з зовнішніми платіжними сервісами або розширена система ролей — без порушення існуючої архітектури.

## 1.7 Розгортання додатку

На поточному етапі розробки застосунок запускається локально та у контрольованому середовищі розробника. Серверна частина запускається командою `python -m src.app` із кореневої директорії репозиторію; використання флагу `-m` є обов'язковим, оскільки всі внутрішні імпорти вказані відносно пакету `src`. База даних PostgreSQL може бути розгорнута локально або надана як хмарний сервіс (наприклад, Supabase, Railway, Neon). Перед запуском необхідно скопіювати та заповнити файл `src/.env` із усіма обов'язковими змінними оточення, а потім виконати `alembic upgrade head` для застосування всіх міграцій схеми.

Для промислового розгортання заплановано контейнеризацію застосунку за допомогою Docker. Передбачуваний підхід — багатоетапна збірка (`multi-stage build`) із мінімальним базовим образом Python, де фінальний образ містить лише залежності з `requirements.txt` та скомпільований код. Оркестрація виконується через `docker-compose`: окремі контейнери для серверної частини, клієнтської частини (React + Nginx) та бази даних PostgreSQL. Змінні оточення передаються через `docker-compose.env` або секрети хмарного провайдера.

Для публічного розгортання рекомендовано наступну типову конфігурацію:

- **Серверна частина** — контейнер FastAPI, запущений через `uvicorn` із кількома воркерами або `gunicorn + uvicorn worker`; розміщення на платформах, що підтримують Docker-образи (Render, Fly.io, Railway, AWS ECS).
- **База даних** — керований PostgreSQL-сервіс із налаштованими резервними копіями та SSL-підключенням.
- **Клієнтська частина** — статична збірка React, що роздається через CDN або Nginx у тому самому `docker-compose`-стеку.
- **Зворотній проксі** — Nginx або Traefik для термінації HTTPS (Let's Encrypt), маршрутизації трафіку між фронтендом і бекендом та стиснення відповідей.

Міграції схеми при розгортанні виконуються як окремий крок ініціалізації (`alembic upgrade head`) до запуску основного контейнера серверної частини — це запобігає умовам гонки між запуском застосунку та незавершеною міграцією.

## 1.8 Логування та метрики

Застосунок реалізує двопотокове логування, налаштоване у `src/config.py` через стандартний модуль Python `logging`. Конфігурація активується при імпорті модуля і не вимагає явного виклику з інших частин коду.

**Перший потік** — текстовий файл `logs.log` у кореневій директорії репозиторію. До нього записуються всі події рівня `INFO` та вище у форматі:

```
YYYY-MM-DD HH:MM:SS,mmm - LEVEL - повідомлення
```

Файл відкривається у режимі дозапису (`mode='a'`), тому перезапуск застосунку не призводить до втрати попередніх записів. Це дозволяє аналізувати хронологію подій та виявляти помилки після факту.

**Другий потік** — вивід у стандартну консоль (`StreamHandler`). Рівень деталізації для консолі встановлено як `DEBUG`, що забезпечує повну діагностичну інформацію під час локальної розробки без забруднення файлу журналу низькорівневими повідомленнями.

Ключові бізнес-події, що логуються явно у відповідних обробниках через `logger.info()`:

| Подія | Місце логування |
|---|---|
| Успішна реєстрація нового користувача | `auth_router.py` |
| Вхід користувача (успішний та невдалий) | `auth_router.py` |
| Завантаження файлу-чека | `file_router.py` |
| Запуск та підсумок cron-задачі оновлення курсів валют | `currency_router.py` |
| Запуск та підсумок cron-задачі рекурентних транзакцій | `recurring_router.py` |

Технічні події (помилки підключення до зовнішніх API, виключення у cron-задачах) логуються через `logger.error()` або `logger.exception()` з повним стек-трейсом, що суттєво прискорює діагностику в production.

У поточній реалізації відсутня інтеграція з зовнішніми системами збору метрик (Prometheus, Grafana, Sentry тощо). Розширення до повноцінного observability-стека є перспективним напрямом розвитку: зокрема, планується інтеграція middleware для вимірювання часу обробки запитів та відстеження частоти помилок за ендпоінтами.
